## Installation (local dev)

```bash
# 1. Clone the repo
git clone <repo-url> microweber
cd microweber

# 2. Install PHP dependencies
composer install --no-interaction --prefer-dist

# 3. Install Node dependencies + build the frontend bundles
npm ci
npm run build

# 4. Bootstrap the .env (see "Environment Variables" below for keys)
cp .env.example .env
php artisan key:generate --ansi

# 5. Database setup (MySQL example — adjust DB_* vars in .env)
mysql -uroot -e "CREATE DATABASE microweber CHARSET utf8mb4 COLLATE utf8mb4_unicode_ci;"
php artisan migrate --seed

# 6. Wire the storage symlink for public uploads
php artisan storage:link

# 7. (Optional) Wire the AI-113 grep-gate as a local pre-commit hook
ln -sf ../../scripts/grep-gate.sh .git/hooks/pre-commit
```

## Same-origin Live-Edit note

Live-edit mounts the user's site inside an `<iframe>` for in-place
WYSIWYG. The parent admin panel and the iframed site **must run on
the same origin** — otherwise the postMessage handshake the toolbar
uses to talk to the canvas fails silently and the editor appears
broken.

Symptoms of cross-origin live-edit:
- Blocks/modules don't drag.
- Inline-text edits don't persist on save.
- Console error: `DOMException: Blocked a frame with origin "X" from accessing a cross-origin frame`.

Fix: ensure `APP_URL`, the admin panel URL, and the iframed site URL
all share the same scheme + host + port. If you're behind a reverse
proxy, set `APP_URL` to the public URL and add a `force_https` config
override.

Cycle-127 (AI-127 / TICKET-BB-EVAL) is evaluating an Origin-header
postMessage check — if it lands strictly, cross-origin setups will
need an explicit allowlist. Until then, single-origin is required.

## Telescope note

Laravel Telescope (`laravel/telescope`) is a dev-only debugging UI.
It records every request, query, exception, mail, etc. — useful in
development, dangerous in production:

- **Never** run Telescope with `APP_ENV=production`. Even a brief
  exposure can leak DB queries, request payloads, session contents,
  and admin tokens into the dashboard.
- The `TelescopeServiceProvider` is gated on `APP_ENV !== 'production'`
  in our config, but the gate is a single line of defense — also
  ensure the route `/telescope` is blocked at the web-server layer
  (nginx / Apache rule) for the production VHOST.
- If you suspect Telescope was briefly accessible in production:
  rotate `APP_KEY` (procedure below), purge the Telescope tables,
  and audit the access logs for `/telescope*` hits.

## App-key rotation procedure

Triggers:
- `APP_KEY` was committed to git or otherwise leaked.
- A previous developer with knowledge of the key has left.
- Quarterly rotation per the security baseline.

Steps:

```bash
# 1. Capture the OLD key — you'll need it during the transition
#    so existing sessions / encrypted DB rows can still be decrypted.
OLD_KEY=$(grep '^APP_KEY=' .env | cut -d= -f2-)

# 2. Generate a NEW key
php artisan key:generate --ansi

# 3. Add the OLD key to APP_PREVIOUS_KEYS so re-encryption can find
#    rows still using the old cipher.
echo "APP_PREVIOUS_KEYS=${OLD_KEY}" >> .env

# 4. Re-encrypt user-encrypted DB rows under the new key.
#    cycle-43 covered users.password_history; cycle-121 (AI-121 /
#    TICKET-BJ) extends the sweep to payment_methods + users.api_token
#    + cms_settings secret rows.
php artisan mw:reencrypt-users          # cycle-43
php artisan mw:reencrypt-payment-methods # cycle-121 (when shipped)
php artisan mw:reencrypt-api-tokens      # cycle-121 (when shipped)
php artisan mw:reencrypt-cms-settings    # cycle-121 (when shipped)

# 5. After verifying every row decrypts cleanly under the NEW key,
#    remove the OLD key from APP_PREVIOUS_KEYS.
sed -i '/^APP_PREVIOUS_KEYS=/d' .env

# 6. Force all sessions to invalidate so existing logged-in users
#    re-authenticate under the new key.
php artisan session:flush       # if your driver supports it
# Or: TRUNCATE TABLE sessions;
```

If the rotation is in response to a known leak: also rotate every
secret stored in `cms_settings` (API keys, mail passwords, etc.),
not just the encryption key.

## Known Setup Gotchas

- **Test memory leak (~6MB per test)** — running the full suite in one
  process OOMs around the 800-test mark. Split into Unit / Feature /
  per-Module groups (the bundled `run-tests.sh` does this). 512MB
  per process is sufficient.
- **No DatabaseTransactions / RefreshDatabase trait** in the project
  test suite — tests are designed for a persistent `microweber_testing`
  DB; the trait would fight the seeding model. (Per project memory
  `feedback_testing`.)
- **No parallel test runs** without explicit isolation — the cart/
  checkout flows use `session_id` collisions that the parallel runner
  doesn't isolate by default.
- **Big2 + Bootswatch templates are separate composer packages** —
  if `Templates/Big2/` is missing locally, contract tests that target
  it (`Big2A11ySweepContractTest`, `Big2MobileAuditContractTest`)
  skip cleanly via `markTestSkipped()`.
- **`public/modules/<module>/` is gitignored** — module asset mirrors
  are produced by `php artisan module:publish` on every deploy. Don't
  edit those directly; edit the source under `Modules/<Module>/resources/assets/`
  and re-publish.
- **Frontend bundle rebuild required** — after editing any `.vue`,
  `.scss`, or `.css` under `packages/`, run `npm run build` and
  verify the rebuilt asset landed under
  `public/vendor/microweber-packages/<pkg>/build/`. The browser
  serves the built bundle, NOT the source.
- **Husky path is sandboxed** — local pre-commit grep-gate lives at
  `scripts/grep-gate.sh` (not `.husky/pre-commit`). Wire via `ln -sf`
  into `.git/hooks/pre-commit` if you want it run on every commit.

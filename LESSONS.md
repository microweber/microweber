## 2026-05-22 — Prefer targeted Blade class change over broad global CSS when a Tailwind utility appears in multiple sibling elements (AI-881 FAIL #3 / task-2026-05-22-ba0702)

- **Pattern:** Dispatch suggested `.p-2 { min-height:44px }` in public-touch.css to fix a cart remove button. The remove button uses `p-2` but so do two non-button siblings in the same Livewire component: `<h3 class="... p-2">` (item title) and `<p class="... p-2">` (price). A global `.p-2 { min-height:44px }` would silently apply to all three — setting `min-height: 44px` on a `<h3>` and `<p>` is not harmful but is unintended. The dispatch explicitly offered "OR change `p-2` → `p-3`" as an alternative.
- **Why it happened:** Tailwind utility classes are semantically atomic — `p-2` means "padding 8px", not "button padding". Any rule targeting `.p-2` at global scope affects every element with that class, not just interactive elements.
- **Prevention rule:** When a Tailwind utility class (or any shared utility class like Bootstrap `.p-N`, `.m-N`, `.text-*`) is used for a fix but the same class appears on non-interactive siblings in the same template, prefer a Blade template change (add a specific class OR change the utility to a higher variant) over a global CSS rule. Reserve global `.utility { min-height }` only when the utility class is EXCLUSIVELY used on interactive elements in the relevant surface. Always grep the same template file for other uses of the targeted class before choosing the CSS approach.
- **Applies when:** Touch-target dispatch for Livewire/Blade components that use Tailwind utility classes; any `min-height`/`min-width` fix where the targeted CSS class is a shared Bootstrap or Tailwind utility rather than a project-specific semantic class.

## 2026-05-22 — Vue SFC scoped styles require `!important` from external override CSS (AI-724 / task-2026-05-22-747f20)

- **Pattern:** ESE angle corner marks (`.angle-top-left`, `.angle-top-right`, `.angle-bottom-left`, `.angle-bottom-right`) use `border: 1px solid #000` set in a Vue SFC `<style scoped>` block. When trying to override from external `element-style-editor.css`, the SFC's `data-v-XXXX` scoped attribute adds specificity: `[data-v-XXXX].angle-top-left { border: 1px solid #000 }` wins over `.angle-top-left { border-color: rgba(255,255,255,0.35) }`.
- **Why it happened:** Vue SFC scoped styles compile to attribute selectors (`[data-v-hash]`) which increase specificity beyond a plain class selector. External CSS files can't add the generated `data-v-hash` attribute to their selectors.
- **Prevention rule:** When overriding Vue SFC scoped styles from an external CSS file (e.g. `element-style-editor.css`), ALWAYS add `!important` to the override declaration. The scoped hash is not knowable at build time in the external file. Apply to all dark-mode ESE overrides that target components rendered inside `<ElementStyleEditorApp>`.
- **Applies when:** Dark-mode overrides in `element-style-editor.css` or `live-edit-classes.css` that target classes used in Vue SFC `<style scoped>` blocks; any external CSS attempting to override styles generated by a Vue SFC `<style scoped>` section.

## 2026-05-22 — PM-suggested CSS selectors must be verified against actual template DOM before adopting (AI-558 / task-2026-05-22-c71042)

- **Pattern:** PM dispatched AI-558 with the fix selector `.blog-posts a, .read-more`. Recon against actual Post module templates found that no template uses `.blog-posts` (without a numeric suffix) — every skin uses `.blog-posts-N` (`.blog-posts-1`, `.blog-posts-2`, etc.). Only two skins had named classes on their read-more links (`.skin-18--read-more-link` + `.mw-post-22-post-read-more`); ~25 other skins use bare `<a class="">` anchors.
- **Why it happened:** PM's dispatch was based on the tester's observation ("text-only links") and a reasonable guess about the container selector, without grepping the actual Blade templates. The real DOM class names follow a skin-specific convention that isn't obvious from module-level inspection.

## 2026-05-22 — Alpine.data() factory must live in @push('scripts'), not in modal Blade view (AI-752 / task-2026-05-22-6eb365)

- **Pattern:** All Add-Content modal cards were invisible despite the source-level fix shipping `x-data="addContentModal"` (bare identifier reference, correct per AI-790). The factory `Alpine.data('addContentModal', factory)` was registered inside the modal Blade view's own `<script>` block. Filament/Livewire morph-inserts the modal HTML when the `+ADD` action mounts; morph-inserted HTML does NOT execute `<script>` tags. The factory therefore never registered → Alpine had no `addContentModal` component → all cards invisible.
- **Why it happened:** The AI-790 fix extracted the factory to a `<script>` block and moved it out of `x-data="..."`, but placed that `<script>` inside the modal's own Blade view. The distinction between "initial page load script execution" and "morph-inserted fragment script execution" wasn't accounted for.
- **Prevention rule:** Any Alpine factory registration (`Alpine.data('name', () => ({...}))`) for a Livewire/Filament-mounted component MUST live in a page-level `@push('scripts')` block that executes on initial page load — not inside the Blade partial that gets morph-inserted. For the Add-Content modal, this is `src/MicroweberPackages/Filament/resources/views/filament/components/layout/live-edit.blade.php` `@push('scripts')`. Additionally, add a `document.addEventListener('livewire:navigated', ...)` listener so the factory re-registers after Livewire v4 SPA navigation.
- **Applies when:** Any `Alpine.data('factoryName', ...)` registration for a component rendered in a Filament modal, Livewire component, or any morph-inserted DOM subtree. If the factory has to be "there when Alpine processes the element", it must be at page load, not in the element's own template fragment.

## 2026-05-22 — Filament v5 anchored picker CSS: `transform: none !important` required (AI-751 / task-2026-05-22-6eb365)

- **Pattern:** The AI-697 anchored Add-Content picker appeared off-screen at runtime despite the source-level CSS setting `transform: none`. Filament v5 applies centering transforms to `.fi-modal-window` elements through its own Tailwind utilities or inline styles. A `transform: none` declaration without `!important` loses to Filament's higher-specificity rule.
- **Why it happened:** The initial AI-697 ship correctly anchored the modal via `position: fixed; top: ...; left: ...`, but the `transform: none` reset that clears Filament's centering animation was missing `!important`. Filament v5's transform either has higher specificity or is an inline style that beats any external CSS without `!important`.
- **Prevention rule:** When anchoring a Filament modal with a CSS override that sets `transform: none` (to clear the browser's built-in centering translate), ALWAYS use `transform: none !important;`. Additionally, add a `max-width: min(var(--size, 42rem), calc(100vw - 80px))` constraint so the modal stays fully visible on narrow viewports. Source-level tests pass (the property is set); only a browser-rendered position probe (Playwright `getBoundingClientRect()`) catches this class of failure.
- **Applies when:** Any CSS rule anchoring a Filament modal to a specific position (top/left offsets) rather than the default centered behavior; any `transform: none` reset in Webpack-bundled `live-edit-classes.css`.

## 2026-05-22 — `strrpos` for last-occurrence task marker when marker appears multiple times (task-2026-05-22-5cbdee)

- **Pattern:** A contract test slicing from a task-ID marker in a CSS file got the wrong block because the marker appeared twice: once in a prior task's comment block that referenced the new fix, and once in the actual new CSS block further down. Using `strpos` found the FIRST occurrence (prior task's comment), so the 1500-char slice didn't reach the new `@media` block, causing the test to false-fail.
- **Why it happened:** CSS files accumulate multiple task-ID markers across blocks. When task-2026-05-22-77c486 (brand mark) included a comment mentioning "task-2026-05-22-5cbdee" (page-header buttons), the 5cbdee marker was present before its own code block. `strpos` is greedy for the first occurrence.
- **Prevention rule:** When a task-ID marker may appear multiple times in the source file (common when a prior task's comment block cites the new task, or when the marker exists in both a CSS comment and in the new rule block), ALWAYS use `strrpos` to find the LAST occurrence. The last occurrence is always the actual new code block. Document in the test docblock why `strrpos` is used: "The marker appears twice: once in [prior context], once in [new block]. `strrpos` finds the LAST occurrence — the new block." Part of the 22+ recurrence selector-self-match guard family.
- **Applies when:** Writing contract tests that use a task-ID marker as a slice anchor in CSS files; any source file where multiple blocks share a marker or where a prior block cites the new task.

## 2026-05-22 — CSS global-scope assertion: position comparison beats slice + @media check (AI-877 / task-2026-05-22-ef3960)

- **Pattern:** Three consecutive iterations of a contract test asserting a CSS rule is at global scope (not inside `@media`) all failed due to `@media` text appearing in the docblock prose ("no @media guard" etc.). The "slice from task marker + check slice doesn't contain @media" approach is fundamentally fragile because the slice can start inside a comment that mentions `@media`.
- **Why it happened:** CSS docblock comments for global-scope rules routinely say things like "no @media guard — applies to all viewports." Any approach that searches for `@media` inside a slice starting from the task marker will false-fail when the marker is inside the comment containing that prose.
- **Prevention rule:** Use the position-comparison approach instead: (a) strip all CSS comments from the full source with `preg_replace('~/\*[\s\S]*?\*/~s', '', $src)`; (b) find the rule selector's LAST position with `strrpos($srcStripped, 'your-selector')`; (c) find the LAST `@media` position with `strrpos($srcStripped, '@media')`; (d) `assertGreaterThan($lastMediaPos, $rulePos)`. If the rule position is after the last `@media` position, it's provably at global scope. If any `@media` appears after the rule, it cannot be at global scope. Robust against all prose variations.
- **Applies when:** Contract-testing that a CSS rule is at global scope (not inside any @media viewport block); asserting "this rule applies to all viewports" for public-touch.css or similar files; any test that previously used "slice from marker + search for @media inside slice."

## 2026-05-22 — Filament v5 inline-style grid override: `.fi-sc-component .mb-6 { display: grid; }` defeats Add Content modal flex layout at ≥640px (AI-870 / task-30040a)

- **Pattern:** The Add Content modal rendered primary card and secondary grid in a flat 2-column grid at 1440px desktop despite AI-692 / AI-713 shipping `display: flex` flex-column layout. The AI-713 fix targeted `.fi-grid` inside the picker, but a DIFFERENT element was the actual cause.
- **Why it happened:** Filament v5 server-renders an inline `<style>` block alongside each `SchemaComponent` with `@media (min-width: 640px) { .fi-sc-component .mb-6 { display: grid; grid-template-columns: 1fr 1fr } }`. The `.mw-add-content-modal-root` div (the root of the blade template) carries Tailwind utility class `mb-6`, so at ≥640px Filament's inline style turned it into a 2-column grid — overriding the blade's `flex flex-col gap-3` classes. Because the inline `<style>` is rendered by the PHP/Filament server layer, it is ABSENT from the static Blade/PHP source files; source-level PHPUnit contract tests pass cleanly while the live DOM shows the wrong layout.
- **Prevention rule:** When a Filament v5 rendered modal or panel shows unexpected layout at runtime despite apparently-correct source-level flex/grid classes, inspect `document.querySelectorAll('style')` (the inline `<style>` blocks) in addition to external stylesheets. Filament injects per-component inline styles server-side that don't appear in the static source. Defeating an inline style requires an `!important` rule in a Webpack-bundled CSS file with a more-specific selector. Always pair the layout fix with a **Tier-1 bundle probe** contract test that reads the served `microweber-filament-theme.css` bundle to confirm the override is delivered (the served-bundle check catches a missing `npm run build`).
- **Discovery pattern for modal layout bugs:** Grid artefact visible at ≥640px but absent at ≤600px → suspect Filament `@media (min-width: 640px)` inline rule → `document.querySelectorAll('style')` in DevTools → look for `.fi-sc-component .mb-6` or similar utility-class-based rules.
- **Applies when:** Debugging unexpected grid/flex layout inside any Filament v5 modal or panel form; adding new layout rules that must override Filament's inline component styles; any "the layout is correct in source but wrong at runtime" scenario for Filament-rendered modals.

## 2026-05-22 — Insert Layout blank-thumbnail root cause: is_file() check at public/ path, not source path (AI-873 / task-2026-05-21-3d7892)

- **Pattern:** All 16 layout cards in the Insert Layout modal showed blank white thumbnail areas. The Vue component was rendering correctly and the layout list was populated. Adding 16 PNG files to the correct path (with no code change) immediately fixed all cards.
- **Why it happened:** `ScanForBladeTemplates.php::scanModuleLayouts()` (lines 286–323) only sets `screenshot_public_url` on a layout entry when `is_file(public_path('templates/<template>/img/screenshots/modules/layouts/templates/<name>.png'))` passes. The Bootstrap template had no screenshots at all → the `if` branch never fired → `screenshot_public_url` was never set → the Vue template rendered a blank div. This is an all-or-nothing gate: there is no fallback placeholder, and the absence produces no error or warning — just silent blank cards.
- **Prevention rule:** When layout cards appear blank in the Insert Layout modal, the diagnostic is: (a) check whether screenshot files exist at `public/templates/<template>/img/screenshots/modules/layouts/templates/*.png`; (b) if absent, they need to be created at BOTH the source path (`Templates/<T>/resources/assets/img/screenshots/…`) AND the served `public/` path (the `is_file()` check reads the public path). Naming convention: replace every `/` in the layout file path with `.` and append `.png` (e.g. `blog/skin-1.blade.php` → `blog.skin-1.png`). Use Big2's screenshot library as ready-made proxies when the target template has no originals — the category names overlap. See `.claude/skills/layout-screenshot-naming/SKILL.md` for the full reference.
- **Applies when:** Adding a new Microweber template that ships custom layouts; investigating blank white thumbnail areas in the Insert Layout (Layouts picker) modal; any `ScanForBladeTemplates.php` debug session.

## 2026-05-18 — Multi-line comment-block grep-asserts: prefer N sequential `assertStringContainsString` over one complex regex (AI-863 / task-77da7a)

- **Pattern:** AI-863 contract test included `js_intercept_removal_carries_explanatory_comment` which initially asserted the multi-line removal-marker comment block via `assertMatchesRegularExpression('~//\s*task-2026-05-18-77da7a\s*/\s*AI-863\s*—\s*JS click-intercept handlers.*REMOVED~is', $blade)`. The `.*` quantifier with `s` modifier should have matched across lines, but the actual comment block had 6 lines of literal newlines + per-line `// ` prefixes + indentation drift between fragments — the regex needed careful escaping for every literal char + multi-line tolerance. First-run test false-failed with a generic "Pattern does not match" message that didn't pinpoint WHICH fragment was missing.
- **Why it happened:** Multi-line regex with `.*` (or `[\s\S]*`) over a heterogeneous comment block is brittle. Every literal `/` `*` `—` `(` `)` needs escaping; newline drift between author + source makes the assertion order-dependent; failure messages give zero diagnostic value. The cost is debugging time for a contract test that ought to be the simplest possible "is this prose here" check.
- **Prevention rule:** When asserting a multi-line comment block (or any multi-fragment prose passage) is present in a source file, ALWAYS prefer N sequential `assertStringContainsString('literal fragment N', $source)` calls — one per distinct fragment — over one `assertMatchesRegularExpression` with `.*` quantifiers spanning the lines. Benefits: (a) failure message names exactly which fragment is missing; (b) no escape gymnastics for `/` `*` `(` etc.; (c) order-independent assertions (PHPUnit checks each fragment individually); (d) future re-formatting of the source comment (indentation, line breaks, punctuation) doesn't false-fail the test as long as the literal fragments survive. Use regex only when the assertion genuinely depends on ORDER (`fragment A before fragment B`) or when fragments contain runtime-variable content.
- **Applies when:** Writing a contract test that asserts a multi-line PHP/Blade/CSS/JS comment block is present near a code change as an audit-trail marker; asserting a multi-paragraph docblock contains certain literal phrases; asserting any prose passage in source.

## 2026-05-18 — Prod request paths must NOT carry fixture-detection logic (un-ship AI-860 per task-4ebf70 human dispatch)

- **Pattern:** AI-860 introduced a `FIXTURE_SLUG_LIKE_PATTERNS` LIKE filter in `Modules/Shop/Livewire/ShopComponent.php` product query + an `AdminFixtureGuard::isFixtureSlug()` `abort(404)` short-circuit in `src/MicroweberPackages/App/Http/Controllers/FrontendController.php` to filter PHPUnit/Faker/Seeder fixture slugs from the public storefront. Designer-approved P1 ship, runtime-verified, contract-tested. **Human owner critique** (task-2026-05-18-4ebf70): "we should not have fixtures in the prod code." The critique is architecturally correct — runtime fixture-detection logic carrying hardcoded patterns like `%test%product%` / `%checkoutresourcetest%` / `%faker%` / `%seeder%` is test-context concern leaking into prod request paths. The pattern set encoded in prod code AS a runtime guard means: (a) every request through the storefront pays the filter cost; (b) every code reviewer sees fixture-handling logic in production; (c) the symbolic ladder ("AdminFixtureGuard" — admin-only name — used on public frontend) communicates a category violation; (d) any legitimate merchant product matching the pattern (real "Test Product Review" content) gets silently 404'd.
- **Why it happened:** When designer audited /shop at HEAD and found `CheckoutResourceTest Product` leaking visibly, the defensive instinct was to filter at runtime. The root cause is data-layer: fixtures had been seeded into the dev DB (via PHPUnit runs creating test products without rollback) and never cleaned up. The defensive runtime filter treats the symptom; the architectural fix is data-layer cleanliness.
- **Prevention rule:** When fixture / test / Faker / Seeder data is visible in a production surface (admin OR public): **first move is DB cleanup, not runtime filter**. Investigate where the fixture data came from (PHPUnit runs without rollback? a `php artisan db:seed` invocation? a migration that inserted demo data?). Fix the source (add rollback to the test class, remove the seeder invocation, revert the demo-data migration). The runtime filter is a band-aid that hides the data-layer problem AND introduces its own maintenance burden (the pattern list rots; legitimate content gets accidentally filtered; the filter cost compounds across pages). **Admin-side fixture filtering remains acceptable** (AdminFixtureGuard's original AI-784 scope — `shouldRenderItem()` / `looksLikeFakerLorem()` / `filterByTitle()` on admin form dropdowns) because admin chrome is operator-facing development UI; admin operators expect to see test/fixture data and want to filter it from picker dropdowns specifically. Public frontend = visitor-facing prod surface; no fixture-detection belongs there.
- **Two-modality split for the AdminFixtureGuard family:** Admin-side AI-784 API (`shouldRenderItem` / `looksLikeFakerLorem` / `filterByTitle` / `FIXTURE_LEAK_PATTERNS` / `FAKER_LOREM_WORDS`) stays — it's correctly scoped to admin form rendering. The AI-860 additions (`FIXTURE_SLUG_LIKE_PATTERNS` / `FIXTURE_SLUG_REGEX_PATTERNS` / `isFixtureSlug()`) are removed — they were the public-side extension that violated the principle.
- **Sentinel pattern for un-shipped runtime filters:** when a runtime filter is un-shipped, INVERT any no-regression sentinels that protected it. Future agents tempted to re-add the filter will false-fail the now-`assertStringNotContainsString` sentinel. Reference: `Public046a37AI861AddToCartCtaContractTest::fixture_filter_runtime_guard_is_removed_per_task_4ebf70`.
- **Applies when:** Reviewing any new public-frontend request path that proposes filtering by test/fixture/Faker/Seeder patterns; rebuilding the dev DB after a session of PHPUnit runs; deciding whether to add a runtime guard vs. a data-layer cleanup.

## 2026-05-17 — Strict-mode global ReferenceError in `packages/frontend-assets/.../tools/` JS bundle (AI-854 / task-f1e4d9)

- **Pattern:** Assignment `url = mw.settings.site_url + ...` (no declarator keyword) inside `common-extend.js:53` linted fine but threw `ReferenceError: url is not defined` at runtime. The dialog never appeared in production; only caught when designer dispatched the regression report.

## 2026-05-17 — PCRE non-greedy quantifiers do NOT respect arbitrary tag boundaries — use per-block-scanner OR negative-lookahead-at-each-position pattern (post-AI-814 Round 14.2 diagnostic refinement, 2-recurrence: AI-809 Group B + AI-814 diagnostic)

- **Pattern:** Designer's Round 14.2 closeout (task-2026-05-17-404500, post-AI-814 ACK) formalised the **PCRE non-greedy quantifier tag-boundary trap** as a generalised sister-rule under the parser-meaningful-character family — now at 2-recurrence in this session. First occurrence: AI-809 Group B contract test regex `lnotif\(([^)]*\$menu_name[^)]*)\)` stopped at the WRONG closing paren when `lnotif()` calls had nested function arguments — the `[^)]*` character class doesn't cross nested parens (parallel to the LESSONS 2026-05-14 contract-test-regex-non-greedy lesson). Second occurrence: AI-814 diagnostic naive-grep `<script>...\{\{[^}]+\}\}...</script>` produced 9 FALSE POSITIVES because Perl/PCRE regex non-greedy quantifiers `[\s\S]+?` happily span multiple `<script>...</script>` blocks PLUS intervening HTML — the regex engine doesn't know `</script>` is a tag boundary; it's just text the quantifier walks through.
- **Why it happens:** PCRE regex engines treat tag boundaries as plain text by default. Non-greedy quantifiers (`.+?` / `[\s\S]+?` / `[^x]*?`) only minimise matched length; they don't ENFORCE boundary semantics. A pattern like `<script>[\s\S]+?</script>` looks like it should match ONE script block — but if the source has two adjacent script blocks `<script>A</script><div>X</div><script>B</script>`, the non-greedy quantifier matches `A</script><div>X</div><script>B` as the inner content of a "single" script block, then matches the final `</script>`. From the regex engine's POV this is a valid single match; from the AUTHOR's POV it's clearly wrong. Same bug at every multi-line construct level: nested parens in function calls (AI-809), tag-bounded element bodies (AI-814), CSS rule bodies, PHP block comments, Blade `@if/@endif` blocks, etc.
- **Prevention rule:** **All bulk-source diagnostic regexes for multi-line constructs (CSS rules, script blocks, HTML elements, PHP closures, Blade blocks) MUST use the per-block-scanner approach OR the negative-lookahead-at-each-position pattern.** Single non-greedy quantifier is unreliable. **Two canonical safe patterns:**
  - **(A) Negative-lookahead-at-each-position:** `<script>(?:(?!</script>).)*?</script>` — the `(?!</script>)` asserts at EVERY position that the next characters are NOT `</script>`, forcing the match to stop at the first occurrence. Generalises: replace `<script>` and `</script>` with your construct's open/close tokens. Works for nested function calls too: `func\((?:(?!\)).)*?\)` matches a single function call body without crossing into the next call.
  - **(B) Per-block-scanner (preferred for production diagnostic scripts):** write a Python/awk/`perl -0777` script that extracts each construct (script block, CSS rule, function body) as a DISCRETE unit, then applies the inner-content regex against each unit individually. The boundary extraction step is explicit + auditable, not embedded in regex magic. Reference: AI-814 diagnostic Python scanner at `/tmp/` extracts each `<script>...</script>` as a separate string before applying the user-data-array-field-access pattern.
- **Applies when:** Authoring any contract test or audit diagnostic that grep-asserts patterns inside multi-line constructs. ESPECIALLY common in: legacy-Blade audit class diagnostics (5-prong recipe), CSS rule-body assertions (every layered-pinning contract test), PHP closure-body assertions, Blade block-body assertions (e.g. asserting absence of legacy text inside a specific `@if` branch). Sister to the unified parser-meaningful-character family meta-rule (4-recurrence: `"` in HTML attribute / `*/` in PHP docblock / `@<directive>` in CSS docblock / `?>` in PHP `//` comment) — both rules share the root: **lexer-level character semantics aren't visible to the regex engine; explicit boundary handling is required.**

## 2026-05-17 — Bulk-template-refactor: preserve original leading-whitespace per-file via regex capture-group + reinjection (NOT assume uniform indentation) — designer-recommended sister-rule to the 5-prong diagnostic

- **Pattern:** Designer's [ACK] AI-812 Pictures empty-state gate (task-2026-05-17-54eecc, commit `4bc3a52ce8`, ×34 recon multiplier across 34 templates) formalised the **indentation-preserving bulk-template-refactor pattern** as a sister-rule to the 5-prong legacy-Blade audit class diagnostic. The AI-812 ship used a Python regex-substitution script (`/tmp/ai_812_pictures_fix.py`) to wrap the existing `<p class="mw-pictures-clean">No pictures added...</p>` else-branch in `@if (is_admin()) ... @endif` across 34 Pictures templates. **Critical defence**: the script captured the ORIGINAL leading whitespace per-file via regex capture group + REINJECTED it on output, rather than assuming uniform indentation. **The Pictures templates carried 3 distinct indent levels in the wild — 12-space, 16-space, and 20-space**. A naive uniform-indentation script would have shipped 22 of the 34 templates with broken Blade indentation (visually identical but indent-mismatched against the surrounding `@foreach`/`@if` blocks); the script's indentation-preserving design prevented this entire failure class.
- **Why it matters:** Bulk-template refactors over module template families (Logo / Page / Menu / Pictures / Teamcard / Posts / etc.) frequently span 10-50 template files. Templates inherited from years of incremental authorship carry inconsistent indentation conventions — some at 12-space (nested-once-in-foreach), some at 16-space (nested-twice), some at 20-space (nested-thrice). Assuming uniform indentation in a search-and-replace script "looks right" on the first 2-3 files inspected but breaks the indentation of the remaining 80%. Manual review across all 34 files would catch the mistake but defeats the bulk-refactor automation. The capture-group reinjection pattern handles ALL indent levels in one pass without per-level branching.
- **Prevention rule (canonical Python recipe):** when authoring a bulk-template-refactor script that touches `<N>` `.blade.php` files via regex substitution, the substitution pattern MUST: (1) capture the leading whitespace of the matched block via `(\s+)` or `(^\s+)` named/numbered group; (2) reinject the captured whitespace as a `\1` (or equivalent) backreference in the replacement; (3) verify the output retains the original indent depth via a post-edit `diff` spot-check on 2-3 files at different indent levels. **Canonical recipe:**
  ```python
  import re
  pattern = re.compile(
      r'(?P<indent>^\s+)<p class="mw-pictures-clean">[^<]*</p>',
      re.MULTILINE
  )
  def replace(m):
      indent = m.group('indent')
      return (
          f'{indent}@if (is_admin())\n'
          f'{indent}    <div class="mw-canvas-empty-state" data-mw-ai780-content-type="picture">\n'
          f'{indent}        <h3>No pictures yet</h3>\n'
          f'{indent}        <p>Add pictures to start your gallery.</p>\n'
          f'{indent}        <a href="{{{{ admin_url(\'media\') }}}}" class="btn btn-primary" aria-label="Add picture">+ Add picture</a>\n'
          f'{indent}    </div>\n'
          f'{indent}@endif'
      )
  src = pattern.sub(replace, src)
  ```
  The `(?P<indent>^\s+)` capture group at the start of each pattern occurrence reads the file's actual indent at that line; the f-string reinjects via `{indent}` on every replacement line. **Verification step**: after running the script, run `git diff --stat` to confirm `<N>` files changed; run `git diff -U0 | grep -E '^[+-]\s+' | awk '{print length($0) - length(ltrim($0))}' | sort -u` to confirm the line-prefix-whitespace distribution matches the original file set.
- **Applies when:** Authoring any bulk-refactor script that touches more than ~5 template files via regex substitution. ESPECIALLY common in: legacy-Blade audit class fix ships where the recon-multiplier is >×5; module-template family sweeps (Pictures × 34, future Slider / Hero / Gallery / Newsletter sweeps if their multipliers cross the bulk-refactor threshold); pre-Filament template normalisation passes. Companion to the 5-prong diagnostic — the diagnostic FINDS the affected files; the indentation-preserving recipe FIXES them safely at scale. Both patterns required for bulk legacy-Blade audit-class ships beyond the single-file scope.
- **Sister-rule (post-AI-813 ACK 2026-05-17 / task-5c6f1e) — Bulk-refactor category ordering:** when a bulk refactor applies MULTIPLE regex categories sequentially (e.g. AI-813 had 4 shape categories — Cat 1 `alt="{{ $item['title'] ?: __('Image') }}"` / Cat 2 `alt="{{ $item['title'] ?? __('Image') }}"` / Cat 3 `responsive_thumbnail(..., ['alt' => __('Image')])` / Cat 4 `image_options['alt-text']` override branch), **topological-sort the categories by post-fix-output dependency**. Each fix's POST-fix output must NOT match ANY subsequent category's PRE-fix regex. Otherwise Cat A's fixed output gets RE-FIXED by Cat B's still-active regex, producing double-replacement bugs. Designer's framing: "Cat 3's post-fix output is a literal subset of Cat 1+2's post-fix output" — so Cat 3 must run AFTER Cat 1+2 (their post-fix output already matches Cat 3's pre-fix pattern, but their fixes are idempotent; running Cat 3 second AGAINST Cat 1+2 post-fix output is a no-op + no-leak). Same selector-self-match family at the FIX-APPLICATION layer (parallel to the test-assertion-layer selector-self-match guard family with 17+ recurrences). Pre-script-run verification: write a small dry-run pass that applies each category's regex against each OTHER category's post-fix output sample + asserts NO overlap. If overlap found, re-order categories OR add anchors to disambiguate. Reference: `/tmp/ai_813_pictures_alt.py` carried the topological-sort discipline + post-fix output verification.

## 2026-05-17 — Data-migration safety toolkit: idempotent-by-construction + cross-driver SQL portability + belt-and-braces shape-match + MySQL SELECT-FROM-SELECT alias

- **Pattern:** Designer's [ACK] AI-791 Slice D + AI-792b bundled data migration (task-2026-05-17-c7156a, commit `c7a85401b4` already shipped, this ACK formalises 4 reusable patterns). The migration cleaned up orphan Blog menu rows + backfilled `layout_file = 'blog.blade.php'` on Content Blog rows. Designer's tier-3 runtime probe confirmed the migration ran as a **clean no-op** on a previously-cleaned install — idempotency-by-construction property held in production conditions. Four patterns from the ship now worth codifying as a reusable toolkit for any future data-migration work:
  - **(1) Idempotent-by-construction migrations:** design the migration so the SAME query shape is safe regardless of install state — clean installs get 0 affected rows, defective installs get N affected rows. No need for an "is the defect present?" pre-check. The migration becomes a no-op when there's nothing to fix. Lets operators run the migration blind without diagnostic conditionals. Anti-pattern: `if (count(orphan_rows) > 0) { delete... }` — branch + diagnostic adds nothing the SQL `WHERE` doesn't already enforce.
  - **(2) Cross-driver SQL portability for test fixtures:** prefer `LIKE 'pattern%' + CHAR_LENGTH(col) = N + SUBSTRING(col, X, Y) REGEXP '[0-9]+'` over raw `col REGEXP 'pattern'`. The decomposed shape works on MySQL AND SQLite (PHPUnit suite + production both supported); raw REGEXP only works on MySQL. PHPUnit suite targets MySQL `microweber_testing` per project convention, but designer fixture-portability discipline keeps the test surface usable against either driver. Example from AI-791 Slice D: `url LIKE 'Blog%' AND CHAR_LENGTH(url) = 18 AND SUBSTRING(url, 5, 14) REGEXP '^[0-9]+$'` matches `Blog{14-digit-timestamp}` portably.
  - **(3) Belt-and-braces shape-match for surgical deletes:** when deleting rows matching a known-shape pattern, restrict via EXACT multi-column match shape the canonical creator method uses (e.g. `createDefaultBlogPage()` creates rows with `content_type='page' + subtype='dynamic' + is_shop=0`). Don't rely on the URL/title column alone — a legitimate user-created row that happens to match the URL pattern would false-delete. Multi-column constraint is the safety belt; single-column match is the suspenders that fails alone. Anti-pattern: `DELETE WHERE url REGEXP '^Blog[0-9]{14}$'` — matches any post titled `Blog20260516195012`, including legitimate user content. Correct shape: same WHERE + `AND content_type = 'page' AND subtype = 'dynamic' AND is_shop = 0`.
  - **(4) MySQL SELECT-FROM-SELECT alias workaround:** when MySQL throws `"can't specify target table 'X' for update in FROM clause"` (the "modify referenced table in subquery" error), wrap the subquery's FROM in an extra layer: `DELETE FROM t WHERE id IN (SELECT id FROM (SELECT id FROM t WHERE ...) AS subq)`. The double-SELECT materializes the inner result before the outer DELETE evaluates the IN clause. SQLite doesn't need this; MySQL does. Cleaner than the alternatives (temp table + multi-statement transaction; or PHP-side fetch + IN-list build).
- **Why it matters / generalisation:** Data migrations are HIGH-BLAST-RADIUS operations — they run on every install regardless of state, run with elevated privileges, and run irreversibly. The 4 patterns above are the defence-in-depth shape for the migration class: (1) protects against running on clean installs (no harm done); (2) protects against driver-specific failures in test fixtures (suite stays portable); (3) protects against false-delete on legitimate user data (multi-column shape-match); (4) protects against MySQL's "can't modify referenced table" runtime error (cleaner than workarounds). Together they form a complete safety envelope for "delete or backfill rows matching a known shape" migrations.
- **Prevention rule:** When authoring ANY data migration that DELETEs or UPDATEs rows by pattern-match, apply the 4-pattern toolkit: **(1)** Make the query idempotent — same query, any install state; no `if (defective)` pre-checks. **(2)** Use `LIKE + CHAR_LENGTH + SUBSTRING REGEXP` over raw `REGEXP` if the migration's test fixtures need to run against both MySQL + SQLite (project-wide PHPUnit convention is MySQL, but defensive portability lets fixtures bypass project DB config for unit-isolation). **(3)** Multi-column shape-match the EXACT shape the canonical creator method produces (`createDefaultBlogPage()` shape: `content_type + subtype + is_shop`). Single-column matches are unsafe. **(4)** If MySQL throws "can't modify referenced table," wrap the subquery FROM in `SELECT * FROM (SELECT ...) AS subq` to materialize. Contract test: assert idempotency property explicitly (run migration twice; second run = 0 affected rows). Reference: `Modules/Content/database/migrations/2026_05_17_000001_ai_791_slice_d_orphan_blog_menu_cleanup_and_ai_792b_layout_backfill.php` + `Content4612c4AI791SliceDOrphanBlogMenuMigrationContractTest` (13 tests / 38 assertions covering 5 safety guards: canonical-exists → delete; sole-orphan → preserve; different-parent → preserve; non-Blog-suffix → preserve; wrong-content-type → preserve).
- **Applies when:** Authoring ANY Laravel migration under `database/migrations/` or `Modules/<Name>/database/migrations/` that touches existing data (DELETE / UPDATE / INSERT-with-conflict-resolution). Especially common for: orphan-row cleanup after bug-fixes; backfill of newly-added columns on existing rows; data-shape normalisation post-refactor; idempotency-by-construction supersedes the older "wrap in transaction + check defective-state-flag" pattern when the SQL itself can express the no-op-on-clean property. Anti-pattern signature: a migration that needs a separate "is the defect present?" diagnostic query before running the fix — that condition belongs IN the WHERE clause, not in PHP control flow.

## 2026-05-17 — Selector-self-match guard two-layer defence (belt + suspenders) + Layer-1 alternative shape: preg_match_all count-comparison — formal sub-rule of the parser-meaningful-character family (17+ session-recurrences)

- **Pattern:** Designer's [ACK] AI-807 docblock-stub-gap follow-up (task-2026-05-17-0cdb52, commit `e79116b70e`) + designer's [ACK] AI-809 Menu $menu_name escape pass (task-2026-05-17-9f5f5a, commit `25acf09569`, this ACK formalises the **count-comparison sub-shape** as a Layer-1 alternative) crystallised the **two-layer defence** for the selector-self-match guard family — now at **17+ session-recurrences** across AI-518/522/531/691a/697/710/711/712/714/715/716/717/718/719/692/790/788/809 + preemptive applications across the AI-803/804/805/816/817/818/840/841 chrome arc. The pattern signature: any contract test asserting ABSENCE of a literal source token (via `assertStringNotContainsString` or a regex like `/<\?php\s+print/`) will false-fail if the same token appears legitimately in the surrounding documentation (docblock prose, inline `//` or `/* */` comments, Blade `{{-- --}}`, CSS `/* */`, HTML `<!-- -->`).
- **Why it happens:** Single-layer defences are brittle. Implementer-only pre-strip catches the test-pass case but leaves the literal token in the source — an outside agent (designer audit, external reviewer, a future agent's diagnostic script) running the same regex VERBATIM against RAW source produces a false-positive hit and triggers an investigation cycle that ends "oh it's just docblock prose". Source-only rephrase catches the verbatim-grep case but is fragile because the implementer's docblock will eventually drift back to citing the literal pattern unless the test ALSO pre-strips defensively. Either layer alone has been observed to drift across the 17-recurrence corpus; the stable solution requires both.
- **Prevention rule (two layers, both required):**
  - **Layer 1 — implementer-side (belt):** pre-strip comments from source BEFORE the negative-regression scan. Canonical recipe: `$stripped = preg_replace('~/\*.*?\*/~s', '', $source); $stripped = preg_replace('~//[^\n]*~', '', $stripped); $stripped = preg_replace('~\{\{--.*?--\}\}~s', '', $stripped);` then assert against `$stripped`. Catches the "my own test passes" case.
  - **Layer 1 ALTERNATIVE SHAPE — preg_match_all count-comparison (cleaner for parens-nesting cases; designer-validated post-AI-809):** when the bad-shape pattern contains nested parens or other regex-engine pitfalls (`[^)]*` doesn't cross nested parens — same family as LESSONS 2026-05-14 contract-test-regex-non-greedy lesson), prefer counting occurrences: `preg_match_all('/raw \$menu_name pattern/', $source, $rawMatches); preg_match_all('/e(\$menu_name) pattern/', $source, $escapedMatches); $this->assertSame(0, count($rawMatches[0])); $this->assertSame($expectedCount, count($escapedMatches[0]));`. The count-comparison shape is **robust against any nesting depth** and avoids the slice-bounding mental model entirely. Designer described this as "the cleaner shape — no slice regex needed." Use when the matched pattern has unbalanced parens, optional nested function calls, or any other regex-engine fragility.
  - **Layer 2 — source-side (suspenders):** rephrase docblock + inline-comment prose to word-form so the literal token does NOT appear in the file the regex scans. Examples: "the legacy unescaped php-print pattern" instead of `<?php print $item[`; "slash-star-style block comment" instead of `*/`; "the else-branch" instead of `@else`; "PHP exits code mode at the php-close-tag" instead of literal `?>`. Catches the "outside auditor runs my literal regex verbatim against raw source" case.
- **Unified sub-rule (subsumes all 17+ recurrences):** **Never write a literal source-token sequence in prose anywhere in the file the regex will scan — rephrase to word-form and/or link to the ticket instead.** This is the canonical sub-rule of the parser-meaningful-character family. Two-layer defence is the IMPLEMENTATION SHAPE of the meta-rule for negative-regression contract tests specifically. Reference codification: AI-807 follow-up `e79116b70e` carries Layer-1 (slice + comment-strip) + Layer-2 (word-form prose); AI-809 `25acf09569` carries Layer-1-alternative (count-comparison via `preg_match_all`) + Layer-2 (word-form prose). Either Layer-1 shape works; choose count-comparison when nesting/parens-balance is fragile.
- **Designer-vs-recon delta caveat** (post-AI-809 ACK 2026-05-17, integrated): designer audits can miss instances when they grep only ONE surface (e.g. the MainDrawer where the editmode lnotif fires) instead of enumerating every module skin. Pattern signature: designer dispatch names N files; recon-grep across the broader module template family finds N+M. For module-template audit-class fixes specifically (Logo / Page / Menu / Pictures / Teamcard / Posts / etc.), ALWAYS run the cross-file diagnostic `grep -rln '<pattern>' Modules/<Name>/resources/views/templates/*.blade.php` before shipping — bundle the extras into the same fix slice with a recon-multiplier note in the SHIP report. AI-809's recon found 2 extra files (images + navbar) beyond designer's 4-named (default + simple + small + skin-1); 33% of installs would have been left vulnerable post-ship without the recon delta. Same defect family as the AI-815 "audit-maturity-as-defense" insight — first-audit modules have HIGH recon multiplier; mature modules have x1.0.
- **Applies when:** Authoring ANY PHPUnit contract test that asserts the ABSENCE of a literal source token. Especially common in: audit-cleanup ships (the removed legacy pattern is referenced in "before/after" docblock prose); Stage-1 consumer-wiring tests (commented-out call site is the negative-assertion target); Stage-3 propagation-without-renderer-update tests ("what was removed" prose appears alongside the negative assertion); Stage-5 template-attribute-escape-leak fixes (rewritten file's docblock describes the corrupted attribute shape). **Skill-file promotion candidate** at 17+ recurrences (well past the 3+ promotion bar); designer explicitly flagged "definitely tier-1 codify when LESSONS next consolidates" — documented as the canonical sub-rule of the parser-meaningful-character family until explicit human direction to author `.claude/skills/selector-self-match-guard/SKILL.md`.

## 2026-05-17 — Parser-meaningful-character family promoted to 4-recurrence + unified meta-rule: any character/sequence with meaning to ANY upstream parser must be escaped or rephrased even inside an apparently-inert context

- **Pattern:** AI-806 (task-2026-05-17-aeb113, commit `9d2e083121`) — Page-template rewrite needed to document the removed legacy `<?php print $item['title'] ?>` pattern in a PHP `//` source comment, but a literal `?>` in a `//` comment terminates PHP code mode at the `?>` (PHP parser exits `<?php ... ?>` at the first `?>` regardless of comment context — the comment is parsed AFTER PHP-mode detection). Fix shape: rephrase the prose as `"the legacy unescaped php-print pattern. PHP exits code mode at ?>"` only when the comment is on its own line AND followed by a newline that re-enters PHP via `<?php`, OR (cleaner) drop the literal token entirely from the prose — `"the legacy unescaped php-print pattern"` carries the same meaning without the parser-meaningful sequence. Designer's Round 13.2 ACK formalised this as the **4th session-occurrence** of the parser-meaningful-character family. **Full family roster:**
  - **(1)** Alpine `x-data="..."` embedded `"` terminates the HTML attribute at the first `"` regardless of surrounding `/* */` or `//` comment context — AI-692 + AI-790 (Alpine x-data factory-extraction is the robust fix).
  - **(2)** PHP docblock prose containing literal `*/` terminates the docblock at the `*/` regardless of surrounding prose — AI-790 (rephrase as words: "slash-star-style block comment").
  - **(3)** Blade `@<directive>` tokens inside CSS docblock comments embedded in `<style>` blocks parse as Blade directives even inside `/* */` CSS comments — AI-796 + AI-803 (rephrase as "else-branch" / "if-statement" / "end-of-if").
  - **(4)** PHP `?>` literal inside a `//` line comment exits PHP code mode at the `?>` regardless of comment context — AI-806 (rephrase or drop the literal token; "the legacy unescaped php-print pattern" without the literal `?>` sequence).
  - **(Bonus, sister family)** VitePress `{{ expression }}` in markdown prose or inline backticks (outside fenced code blocks) is parsed by Vue at SSR — AI-326 docs hardening sweep (escape with `&#123;&#123;`).
- **Why it happens:** Each instance is the same mental-model bug — author assumes "this is inside a comment, the upstream parser will skip it." False at every layer. Parser-meaningful characters (`"`, `*/`, `@<directive>`, `?>`, `{{`) terminate or alter their enclosing structure at the LEXER stage, before the comment is recognised. The unifying mental model that prevents the bug: **comments are not safe containers for parser-meaningful tokens; they're inline text the parser sees in the same pass as the surrounding code.**
- **Prevention rule (unified meta-rule):** **Any character or sequence with meaning to ANY upstream parser MUST be escaped or rephrased even inside an apparently-inert context** — `//` line comments, `/* */` block comments, CSS comments inside `<style>`, prose inside `@php @endphp`, prose inside docblocks, JS template literals, HTML attribute values, markdown prose. Examples: "slash-star-style block comment" not `*/`; "the else-branch" not `@else`; "the legacy php-print pattern" not `?>`; "the HTML-attribute quote terminator" not the bare `"`. Contract-test regression guard pattern: assert the affected source file does NOT contain the literal parser-meaningful token outside of its legitimate code-mode use. Same family lineage now spans 4 distinct token classes + 1 markdown sibling; codify the meta-rule when authoring ANY new comment / docblock / prose surface that references removed-code patterns.
- **Applies when:** Authoring or auditing any source file with embedded prose that references the SHAPE of removed/legacy code. ESPECIALLY common in Blade view rewrites + Filament resource refactors + Alpine factory extractions + PHP class deprecations — anywhere the docblock explains "what this used to be" using literal tokens from the prior shape. The recurrence rate is now 4 in one session; future contract tests should preemptively pin parser-meaningful-token absence in the rewritten source as a regression guard. ## 2026-05-17 — Contract-test source slicing: never bound on `strpos($source, ';', ...)` when surrounding docblock prose may contain semicolons

## 2026-05-17 — Stage-6 JS-context-escape-leak: Blade `{{ }}` HTML-escapes but does NOT JS-escape

- **Pattern:** Designer's Round 14.2 audit (task-2026-05-17-4054e4 STATUS roll-up, dispatched after AI-814 ship) explicitly proposed codifying a **new Stage in the failure-family taxonomy**: "JS-context escape is its own Stage — Blade `{{ }}` doesn't help here." The AI-814 defect is the canonical instance: `description: "{{ $item['title'] }}"` interpolated inside a `<script>` block. Blade's `{{ }}` HTML-escapes (`<` → `&lt;`, `&` → `&amp;`, `"` → `&quot;`, etc.) but `<script>` content is NOT subject to HTML entity decoding by the browser. A title containing `</script><script>alert(1)</script>` would be HTML-escaped to `&lt;/script&gt;...` (literal text inside the JS string, safe in modern browsers) — BUT a title containing a literal `"` becomes `&quot;` which is rendered as 6 literal characters inside the JS string, not as `"`. The string still doesn't break out, BUT the rendered content is corrupted (display shows `John&quot;s` instead of `John"s`). More importantly, depending on browser + Content-Security-Policy + locale + Blade-render order, **defense-in-depth requires JS-context-aware escape**, NOT HTML-context. Confirmed surfaces: AI-814 (Pictures module gallery<rand> script block) — 6 templates. Sibling to Stage-5 template-attribute-escape-leak (AI-692/AI-790 — HTML attribute context); Stage-6 covers the `<script>` block JS-string-literal context.
- **Why it happened:** Blade `{{ }}` is the project's canonical "escape for safe output" idiom. Developers reasonably assume `{{ }}` is universally safe across HTML / attribute / script / style contexts. It isn't: each context has its own escape rules. `{{ }}` is wrong for JS-string-literal context (use `json_encode()` with JS-context flags), wrong for CSS-value context (use a sanitised allowlist), and risky for HTML-attribute context if the attribute body contains JS expressions (AI-692 Alpine x-data lineage). The unifying mental-model bug is "HTML escape = safe everywhere" — false. Designer crystallised the lesson: *"Blade `{{ }}` doesn't help here, you need `json_encode()` with `JSON_HEX_*` flags OR move the data to a `data-` attribute and read it via JS."*
- **Prevention rule:** Never interpolate user-controllable data directly inside a `<script>` block via Blade `{{ }}`. Two canonical safe patterns: **(A) `json_encode($data, JSON_HEX_QUOT | JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS)`** — the canonical **4-flag combination** (designer-validated post-AI-814 ACK 2026-05-17 as the "canonical 'escape all JS-context characters as `\uXXXX`' recipe") that escapes `"` (JSON_HEX_QUOT), `<` + `>` (JSON_HEX_TAG), `&` (JSON_HEX_AMP), `'` (JSON_HEX_APOS) as `\uXXXX` sequences inside the JSON output. All four flags required — dropping any one leaves the corresponding character un-escaped + opens the corresponding JS-context exit vector. Ship as `<script>window.foo = @php echo json_encode(...); @endphp;</script>`. **(B) Move the data to a `data-*` attribute on a static DOM node** (where Blade `{{ }}` IS the correct escape because HTML attribute context decodes entities), then read in JS via `JSON.parse(el.dataset.foo)`. Pattern (A) is preferred for inline initialisation; pattern (B) is preferred for data that's already DOM-bound. Wrap any initialisation in an IIFE `(function () { ... })();` to avoid global scope pollution, AND use explicit `window.foo = ...` assignment if the global IS intentional so external readers find it by name. Reference: AI-814 / task-2026-05-17-8cf71e — 6 Pictures templates closed by this recipe with the 4-flag combination shipping `JSON_HEX_QUOT | JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS` in 8 total Fix-B replacements pinned by Group A/B/C/D/E/F contract test (56 tests / 125 assertions).
- **Applies when:** Authoring any Blade template that emits a `<script>` block containing variables sourced from user-controllable data (`$item['title']`, `$post['description']`, `$user['name']`, `$content_id`, anything from the request, anything from the database). ESPECIALLY when initialising JS gallery / lightbox / modal / autocomplete data structures inside `<script>` blocks where multiple per-item values are interpolated. Family lineage: Stage-5 (HTML-attribute-escape-leak — AI-692/790) + Stage-6 (JS-context-escape-leak — AI-814, this entry).
- **Diagnostic-grep refinement (codified post-AI-814 from Round 14.2 STATUS roll-up false-positive audit):** the naive single-regex prong `grep -rE '<script>...\{\{[^}]+\}\}...</script>'` does NOT work reliably because Perl/PCRE regex engines do not respect `</script>` as a tag boundary — non-greedy `[\s\S]+?` happily spans multiple `<script>...</script>` blocks PLUS the intervening HTML, producing false matches like the AI-814 cycle's 9 false positives across 7 modules (Accordion / BeforeAfter / Captcha / Cart / CustomFields / HighlightCode / Menu / Pictures-slick). All 9 turned out to interpolate only TRUSTED data sources (`{{ $params['id'] }}`, `{{ asset() }}`, `{{ __() }}`, `{{ admin_url() }}`, `{{ get_option() }}`, `{{ app()->getLocale() }}`, `{{ $id }}`, `{{ $before }}`, `{{ $for_id }}`, `{{ $edit_field_key }}`). **Correct diagnostic methodology:** use a per-script-block scanner (Python / `awk` / `perl -0777` with explicit `(?:(?!</script>).)*?` non-crossing-tag pattern) — NOT a single-line `grep` regex. The scanner extracts each `<script>...</script>` block as a discrete unit, then asserts the script body contains a Blade interpolation of the shape `\{\{\s*\$(item|post|content|user|comment|record|product|category|page)\[` (user-data array-field access). Reference Python implementation lives in `/tmp/` for ad-hoc audit runs — `grep` alone is insufficient. **General lesson for all stage-family diagnostics:** (a) prefer per-construct scanners over single-line regexes when the construct boundary matters; (b) always exclude trusted-helper-output patterns from the prong; user-data array-field access is the canonical defect signature.

## 2026-05-17 — Blade `@<directive>` tokens inside CSS docblock comments crash the Blade compiler (2-recurrence promotion)

- **Pattern:** Now 2 session-recurrences. (1) task-2026-05-17-0e6cfa (AI-796 cart empty-state) — wrote `/* Livewire CartItems @else branch renders ... */` inside a CSS docblock in `<style>` block; Blade crashed live page with "syntax error, unexpected end of file, expecting elseif/else/endif". (2) task-2026-05-17-fa5dc3 (AI-803 Logo SCSS) — wrote prose describing the AI-805 dead-conditional block including the literal `@if(is_live_edit())` token in a CSS docblock; same crash. Both bugs invisible to source-level contract tests (compile-stage failure happens before any test fixture loads); both invisible to `php -l` (syntactically valid PHP because Blade compilation is a separate pass).
- **Why it happened:** The Blade compiler (`Illuminate\View\Compilers\BladeCompiler`) parses `@<directive>` tokens with regex passes BEFORE CSS comments are recognised as comments — CSS `/* ... */` is plain text to Blade. The Blade `@if` / `@else` / `@elseif` / `@endif` directives need balanced opening/closing pairs; when a `@if(` appears in prose without a matching `@endif`, Blade walks to EOF looking for one and fails with the line-anchored compile error. Symmetric: `@else` / `@endif` appearing without a preceding `@if` opener also confuse the matcher. The author's mental model — "this is inside a CSS comment, the compiler will skip it" — is wrong because Blade doesn't know CSS.
- **Prevention rule:** Never write literal `@if(` / `@else` / `@elseif` / `@endif` / `@switch(` / `@case(` / `@foreach(` / `@for(` / `@while(` tokens inside ANY content embedded in a Blade view — including CSS comments inside `<style>`, HTML comments, JS template literals inside `<script>`, prose inside `@php ... @endphp` blocks. Rephrase: "the if-statement at line N" / "the else-branch" / "the end of the if-block" / "the at-if-paren-X-paren conditional"; or break the token sequence with prose-only words ("the directive that opens with at-if"). The rule applies to ANY content the Blade compiler sees — Blade reads the whole file before deciding what's a directive. ## 2026-05-16 — Vue popover dismiss handlers MUST use capture phase, never default bubble

- **Pattern:** task-66ceca AI-701 PageChip popover initially registered its outside-click dismiss as `document.addEventListener('click', handleOutsideClick)` (default = bubble phase). Clicking outside the popover did not close it — testing with Playwright showed the listener was attached, but `stopPropagation()` calls inside Filament/Livewire/Alpine internals (mostly used for their own modal/dropdown dismissal) cancelled the bubble before it reached `document`.

- **Applies when:** Authoring any Vue/Alpine popover, dropdown, dismissable card, or menu in `packages/frontend-assets/resources/assets/ui/`. The same rule applies to JS event listeners registered from a Blade `<script>` block where the surrounding page may contain Filament/Livewire/Alpine modals.

## 2026-05-16 — `/* … */` block comments inside an HTML attribute value terminate the attribute at the first embedded `"`

- **Pattern:** task-968a71 first-attempt at the AI-692 two-group Add-Content modal embedded a block comment in the `x-data="..."` Alpine attribute that contained prose like `/* typing "page" hides the "On this page" group header */`. ## 2026-05-16 — Tailwind v4 uses native CSS `translate` property — independent of `transform`

- **Pattern:** task-02760c (Live Edit sidebar menu invisible after hamburger click) hit a silent regression where the project's `.fi-sidebar { transform: translateX(-100%) !important }` override appeared to do nothing. DevTools confirmed `transform: matrix(1, 0, 0, 1, 0, 0)` (identity!) but `getBoundingClientRect().x === -280`. Root cause: Tailwind v4 compiles utilities like `-translate-x-full` to the **native CSS `translate` property** (`translate: -100% !important`), NOT to `transform: translateX(...)`. CSS `translate` is its own property — independent of `transform` — and the Tailwind utility wins because the project override never touches it.
- **Why it happened:** The `transform: translateX(...)` mental model is the Tailwind v3 / pre-2022 CSS shape; Tailwind v4 adopted the newer CSS individual-transform properties. Project-side overrides written against v3 muscle memory silently miss the v4 generated CSS.
- **Prevention rule:** When defeating any Tailwind v4 translate/rotate/scale utility, reset BOTH the individual property AND the composite `transform`: `translate: none !important; transform: translateX(-100%) !important;` (also `rotate: none !important;` / `scale: none !important;` as applicable). Validate with `getComputedStyle(el).translate` not just `.transform`. Always reproduce at the failing viewport with Playwright + `evaluate(() => getBoundingClientRect())` before declaring the override correct.
- **Applies when:** Any project-side CSS attempting to override a Tailwind v4 utility that animates element position. Common spots: Filament sidebar/topbar visibility toggles, modal slide-in/out, drawer opens.

## 2026-05-17 — Tier-3 runtime-probe stale-bundle hazard: always `location.reload()` between bundle-rebuild and runtime-probe (sister-rule to the multi-bundle-freshness gotcha family)

- **Pattern:** Designer's [ACK] AI-811 ResolutionSwitch semantic upgrade (task-2026-05-17-6626cd, commit `ecabe27ec8` already shipped) formalised the **stale-bundle hazard during Tier-3 runtime probe**. After my AI-811 ship rebuilt the frontend-assets Vite bundle (`live-edit-app.js` etc.), designer's first Tier-3 browser probe at `/admin/live-edit` returned the OLD DOM: `<SPAN role="button" aria-pressed>` (the pre-fix shape AI-811 was meant to replace). The contract test's runtime-bundle-presence assertion was green (served bytes contained the new `<button role="radio" aria-checked>` shape), but the browser had cached the PRE-fix bundle from the prior session and continued serving it from disk-cache until forced to reload. After `location.reload()` the new `<BUTTON role="radio" aria-checked>` markup landed clean.
- **Why it happens:** Vite/Webpack produce content-hashed bundle filenames (e.g. `live-edit-app.eb1ac3e79.js`) precisely to defeat browser caching across rebuilds — BUT the HTML page that references those bundles is itself often served from disk cache on a SPA-style navigation. The browser observes "URL `/admin/live-edit` hasn't changed → reuse cached HTML → reuse the OLD content-hash filename inside the HTML → serve the OLD bundle." Only a HARD reload (Cmd-Shift-R / DevTools "Empty cache and hard reload" / programmatic `location.reload()`) forces the browser to re-fetch the HTML wrapper + discover the new content-hash. The contract test's runtime-bundle-presence assertion validates SERVED bytes (HTTP fetch of `public/vendor/.../live-edit-app.css` mtime + content), not what the browser ACTUALLY LOADED — the two diverge during the probe.
- **Prevention rule:** When verifying ANY ship that includes a JS-bundle rebuild (frontend-assets Vite OR microweber-filament-theme Webpack OR frontend-assets-libs build.mjs), the Tier-3 runtime probe MUST: (1) navigate to the target URL; (2) execute `location.reload()` programmatically (Playwright: `await page.reload({ waitUntil: 'networkidle' })`) OR DevTools "Empty cache and hard reload" if probing manually; (3) THEN read runtime DOM state. Without step 2, the browser may serve the PRE-fix bundle for the entire session — Tier-3 probe results are stale + appear to contradict the source change. Pair with Tier-2 contract-test runtime-bundle-presence assertion (bundle mtime ≥ source mtime, established post-task-bc28fd) so the two layers verify different aspects: contract test validates SERVED bytes; Tier-3 probe with forced reload validates BROWSER-LOADED bytes. Both required; either alone is insufficient — bc28fd two-stage-CSS rule (source + served-bundle) was the predecessor of THIS lesson (browser-loaded — the third stage).
- **Applies when:** Verifying ANY ship that rebuilds a JS or CSS bundle the browser caches. ESPECIALLY common in: Vue SFC ships (Toolbar.vue, ResolutionSwitch.vue, SaveButton.vue); Vite output rebuilds; Webpack output rebuilds; design-token `:root` overrides that cascade into Filament-rendered DOM; any ship where contract-test bundle-mtime check passes but runtime probe returns the OLD shape. Sister-rule progression: **bc28fd (source + served-bundle) → AI-811 ACK (served-bundle + browser-loaded)** — together they form a 3-stage verification chain (source → served → loaded). The 3rd stage requires the forced-reload step in Tier-3 probe protocol.

## 2026-05-17 — Layout-budget-token shrink two-layer defence: component-level constraint + container-level token-anchor (post-AI-810 ACK; sister-rule to fix-once-pin-both-layers)

- **Pattern:** Designer's [ACK] AI-810 Resolution-switcher clip fix (task-2026-05-17-5d3963, commit `eeb1ac3e79`) formalised the **two-layer defence pattern for layout-budget-token changes**. AI-810 surfaced when AI-698a (task-ec0c87) shrunk `--toolbar-height` from 60px → 48px. The `.toolbar-col` parent flex container carried `flex-wrap: wrap; gap: 20px;` with no height constraint — at 60px budget the wrapped two-row layout still fit; at the new 48px budget the wrap pushed `#preview-nav` top to `-19.5px` (top half clipped above viewport). Single-layer fixes were insufficient: (a) component-only fix (`flex-nowrap` on the inner flex container in `Toolbar.vue:125`) prevented WRAP but left the item-exceeds-budget scenario open (a future taller child would still clip); (b) container-only fix (`min-height: var(--toolbar-height); align-items: center` on parent) anchored the frame but didn't prevent the wrap-triggered clip. **Two-layer fix shipped** as the canonical defence:
  - **Layer 1 — component-level (consumer-side):** prevent wrap at the consumer's flex container. AI-810: `Toolbar.vue:125` `<div class="d-flex align-items-center flex-nowrap gap-2">` (was `flex-wrap gap-2`).
  - **Layer 2 — container-level (token-anchor):** anchor the container's height/width to the layout-budget token + `align-items: center` (or `justify-content: center` for the horizontal axis). AI-810: `index.css .toolbar-col { display: flex; flex-wrap: nowrap; gap: 20px; min-height: var(--toolbar-height); height: var(--toolbar-height); align-items: center; }` — `min-height` + `height` both anchored to the token so even a future taller child component stays vertically centred within the 48px frame.
- **Why it happens / why two layers:** When a layout-budget CSS token shrinks, the WRAP scenario manifests first (existing content overflows the new budget axis), but the **item-exceeds-budget scenario** is a separate failure mode — a future child component naturally larger than the new budget will clip again regardless of wrap. Single-layer defence at either layer alone is brittle: component-only fixes the wrap but not the overflow; container-only fixes the overflow but not the wrap. Two-layer defence prevents BOTH manifestations + provides defence-in-depth against future regressions (sibling refactor adding a taller child, future budget shrink, etc.).
- **Prevention rule:** When fixing a layout-budget-token-shrink defect (consumer clips/wraps inside a frame that shrunk), apply BOTH layers explicitly: (Layer 1) constrain the consumer's flex/grid behaviour (`flex-nowrap`, `overflow: hidden`, `max-width: 100%`, etc.) so the WRAP/overflow can't manifest; (Layer 2) anchor the container's relevant dimension to the budget token (`min-height: var(--<token>); height: var(--<token>); align-items: center`) so even an out-of-spec future child stays positioned. Contract test pins BOTH layers + adds a browser-rendered-position probe asserting the coordinate invariant (e.g. `previewNavRect.top > 0`, `previewNavRect.bottom <= toolbarHeight`). The two-layer pattern generalises across both AXES of the viewport-scope-leak family (horizontal: AI-803 logo; vertical: AI-810 toolbar) — sister-rule to the AI-808 ACK "fix-once-pin-both-layers" rule for shared-primitive ships. Reference: AI-810 fix at `eeb1ac3e79` carries both layers + `LiveEditB91c0cAI810ResolutionSwitcherClippingContractTest` (8 tests / 25 assertions) pins both source-level + Tier-3 runtime probe at `previewNavTopGreaterThanZero: true`.
- **Applies when:** Authoring or auditing any CSS rule that consumes a layout-budget token via `var(--<token>)` AND the consumer takes content-natural sizing through the frame. Especially common in: toolbar/sidebar/modal/dialog height/width tokens that shrink across refactors; flex/grid container parents where children take content-natural sizing; surface refreshes that change a layout-budget token (AI-698a `--toolbar-height` 60 → 48 is the canonical trigger). The two-layer pattern joins the existing layered-pinning lessons (bc28fd two-stage-CSS + AI-816 Slice B audit-the-base-class + AI-808 fix-once-pin-both + this AI-810 layout-budget two-layer) — meta-pattern emerging: **all CSS layout fixes inside consumer-of-shared-primitive contexts need explicit per-layer pinning, not single-layer assumption.**

## 2026-05-17 — Data-migration safety toolkit: idempotent-by-construction + cross-driver SQL portability + belt-and-braces shape-match + MySQL SELECT-FROM-SELECT alias

- **Pattern:** Designer's [ACK] AI-791 Slice D + AI-792b bundled data migration (task-2026-05-17-c7156a, commit `c7a85401b4` already shipped, this ACK formalises 4 reusable patterns). The migration cleaned up orphan Blog menu rows + backfilled `layout_file = 'blog.blade.php'` on Content Blog rows. Designer's tier-3 runtime probe confirmed the migration ran as a **clean no-op** on a previously-cleaned install — idempotency-by-construction property held in production conditions. Four patterns from the ship now worth codifying as a reusable toolkit for any future data-migration work:
  - **(1) Idempotent-by-construction migrations:** design the migration so the SAME query shape is safe regardless of install state — clean installs get 0 affected rows, defective installs get N affected rows. No need for an "is the defect present?" pre-check. The migration becomes a no-op when there's nothing to fix. Lets operators run the migration blind without diagnostic conditionals. Anti-pattern: `if (count(orphan_rows) > 0) { delete... }` — branch + diagnostic adds nothing the SQL `WHERE` doesn't already enforce.
  - **(2) Cross-driver SQL portability for test fixtures:** prefer `LIKE 'pattern%' + CHAR_LENGTH(col) = N + SUBSTRING(col, X, Y) REGEXP '[0-9]+'` over raw `col REGEXP 'pattern'`. The decomposed shape works on MySQL AND SQLite (PHPUnit suite + production both supported); raw REGEXP only works on MySQL. PHPUnit suite targets MySQL `microweber_testing` per project convention, but designer fixture-portability discipline keeps the test surface usable against either driver. Example from AI-791 Slice D: `url LIKE 'Blog%' AND CHAR_LENGTH(url) = 18 AND SUBSTRING(url, 5, 14) REGEXP '^[0-9]+$'` matches `Blog{14-digit-timestamp}` portably.
  - **(3) Belt-and-braces shape-match for surgical deletes:** when deleting rows matching a known-shape pattern, restrict via EXACT multi-column match shape the canonical creator method uses (e.g. `createDefaultBlogPage()` creates rows with `content_type='page' + subtype='dynamic' + is_shop=0`). Don't rely on the URL/title column alone — a legitimate user-created row that happens to match the URL pattern would false-delete. Multi-column constraint is the safety belt; single-column match is the suspenders that fails alone. Anti-pattern: `DELETE WHERE url REGEXP '^Blog[0-9]{14}$'` — matches any post titled `Blog20260516195012`, including legitimate user content. Correct shape: same WHERE + `AND content_type = 'page' AND subtype = 'dynamic' AND is_shop = 0`.
  - **(4) MySQL SELECT-FROM-SELECT alias workaround:** when MySQL throws `"can't specify target table 'X' for update in FROM clause"` (the "modify referenced table in subquery" error), wrap the subquery's FROM in an extra layer: `DELETE FROM t WHERE id IN (SELECT id FROM (SELECT id FROM t WHERE ...) AS subq)`. The double-SELECT materializes the inner result before the outer DELETE evaluates the IN clause. SQLite doesn't need this; MySQL does. Cleaner than the alternatives (temp table + multi-statement transaction; or PHP-side fetch + IN-list build).
- **Why it matters / generalisation:** Data migrations are HIGH-BLAST-RADIUS operations — they run on every install regardless of state, run with elevated privileges, and run irreversibly. The 4 patterns above are the defence-in-depth shape for the migration class: (1) protects against running on clean installs (no harm done); (2) protects against driver-specific failures in test fixtures (suite stays portable); (3) protects against false-delete on legitimate user data (multi-column shape-match); (4) protects against MySQL's "can't modify referenced table" runtime error (cleaner than workarounds). Together they form a complete safety envelope for "delete or backfill rows matching a known shape" migrations.
- **Prevention rule:** When authoring ANY data migration that DELETEs or UPDATEs rows by pattern-match, apply the 4-pattern toolkit: **(1)** Make the query idempotent — same query, any install state; no `if (defective)` pre-checks. **(2)** Use `LIKE + CHAR_LENGTH + SUBSTRING REGEXP` over raw `REGEXP` if the migration's test fixtures need to run against both MySQL + SQLite (project-wide PHPUnit convention is MySQL, but defensive portability lets fixtures bypass project DB config for unit-isolation). **(3)** Multi-column shape-match the EXACT shape the canonical creator method produces (`createDefaultBlogPage()` shape: `content_type + subtype + is_shop`). Single-column matches are unsafe. **(4)** If MySQL throws "can't modify referenced table," wrap the subquery FROM in `SELECT * FROM (SELECT ...) AS subq` to materialize. Contract test: assert idempotency property explicitly (run migration twice; second run = 0 affected rows). Reference: `Modules/Content/database/migrations/2026_05_17_000001_ai_791_slice_d_orphan_blog_menu_cleanup_and_ai_792b_layout_backfill.php` + `Content4612c4AI791SliceDOrphanBlogMenuMigrationContractTest` (13 tests / 38 assertions covering 5 safety guards: canonical-exists → delete; sole-orphan → preserve; different-parent → preserve; non-Blog-suffix → preserve; wrong-content-type → preserve).
- **Applies when:** Authoring ANY Laravel migration under `database/migrations/` or `Modules/<Name>/database/migrations/` that touches existing data (DELETE / UPDATE / INSERT-with-conflict-resolution). Especially common for: orphan-row cleanup after bug-fixes; backfill of newly-added columns on existing rows; data-shape normalisation post-refactor; idempotency-by-construction supersedes the older "wrap in transaction + check defective-state-flag" pattern when the SQL itself can express the no-op-on-clean property. Anti-pattern signature: a migration that needs a separate "is the defect present?" diagnostic query before running the fix — that condition belongs IN the WHERE clause, not in PHP control flow.

Three layered-pinning lessons now form a coherent meta-pattern: **all bounded-slice contract tests should explicitly enumerate "what layers does this fix depend on" and pin each one independently.**

## 2026-05-17 — Selector-self-match guard two-layer defence (belt + suspenders) + Layer-1 alternative shape: preg_match_all count-comparison — formal sub-rule of the parser-meaningful-character family (17+ session-recurrences)

- **Pattern:** Designer's [ACK] AI-807 docblock-stub-gap follow-up (task-2026-05-17-0cdb52, commit `e79116b70e`) + designer's [ACK] AI-809 Menu $menu_name escape pass (task-2026-05-17-9f5f5a, commit `25acf09569`, this ACK formalises the **count-comparison sub-shape** as a Layer-1 alternative) crystallised the **two-layer defence** for the selector-self-match guard family — now at **17+ session-recurrences** across AI-518/522/531/691a/697/710/711/712/714/715/716/717/718/719/692/790/788/809 + preemptive applications across the AI-803/804/805/816/817/818/840/841 chrome arc. The pattern signature: any contract test asserting ABSENCE of a literal source token (via `assertStringNotContainsString` or a regex like `/<\?php\s+print/`) will false-fail if the same token appears legitimately in the surrounding documentation (docblock prose, inline `//` or `/* */` comments, Blade `{{-- --}}`, CSS `/* */`, HTML `<!-- -->`).
- **Why it happens:** Single-layer defences are brittle. Implementer-only pre-strip catches the test-pass case but leaves the literal token in the source — an outside agent (designer audit, external reviewer, a future agent's diagnostic script) running the same regex VERBATIM against RAW source produces a false-positive hit and triggers an investigation cycle that ends "oh it's just docblock prose". Source-only rephrase catches the verbatim-grep case but is fragile because the implementer's docblock will eventually drift back to citing the literal pattern unless the test ALSO pre-strips defensively. Either layer alone has been observed to drift across the 17-recurrence corpus; the stable solution requires both.
- **Prevention rule (two layers, both required):**
  - **Layer 1 — implementer-side (belt):** pre-strip comments from source BEFORE the negative-regression scan. Canonical recipe: `$stripped = preg_replace('~/\*.*?\*/~s', '', $source); $stripped = preg_replace('~//[^\n]*~', '', $stripped); $stripped = preg_replace('~\{\{--.*?--\}\}~s', '', $stripped);` then assert against `$stripped`. Catches the "my own test passes" case.
  - **Layer 1 ALTERNATIVE SHAPE — preg_match_all count-comparison (cleaner for parens-nesting cases; designer-validated post-AI-809):** when the bad-shape pattern contains nested parens or other regex-engine pitfalls (`[^)]*` doesn't cross nested parens — same family as LESSONS 2026-05-14 contract-test-regex-non-greedy lesson), prefer counting occurrences: `preg_match_all('/raw \$menu_name pattern/', $source, $rawMatches); preg_match_all('/e(\$menu_name) pattern/', $source, $escapedMatches); $this->assertSame(0, count($rawMatches[0])); $this->assertSame($expectedCount, count($escapedMatches[0]));`. The count-comparison shape is **robust against any nesting depth** and avoids the slice-bounding mental model entirely. Designer described this as "the cleaner shape — no slice regex needed." Use when the matched pattern has unbalanced parens, optional nested function calls, or any other regex-engine fragility.
  - **Layer 2 — source-side (suspenders):** rephrase docblock + inline-comment prose to word-form so the literal token does NOT appear in the file the regex scans. Examples: "the legacy unescaped php-print pattern" instead of `<?php print $item[`; "slash-star-style block comment" instead of `*/`; "the else-branch" instead of `@else`; "PHP exits code mode at the php-close-tag" instead of literal `?>`. Catches the "outside auditor runs my literal regex verbatim against raw source" case.
- **Unified sub-rule (subsumes all 17+ recurrences):** **Never write a literal source-token sequence in prose anywhere in the file the regex will scan — rephrase to word-form and/or link to the ticket instead.** This is the canonical sub-rule of the parser-meaningful-character family. Two-layer defence is the IMPLEMENTATION SHAPE of the meta-rule for negative-regression contract tests specifically. Reference codification: AI-807 follow-up `e79116b70e` carries Layer-1 (slice + comment-strip) + Layer-2 (word-form prose); AI-809 `25acf09569` carries Layer-1-alternative (count-comparison via `preg_match_all`) + Layer-2 (word-form prose). Either Layer-1 shape works; choose count-comparison when nesting/parens-balance is fragile.
- **Designer-vs-recon delta caveat** (post-AI-809 ACK 2026-05-17, integrated): designer audits can miss instances when they grep only ONE surface (e.g. the MainDrawer where the editmode lnotif fires) instead of enumerating every module skin. Pattern signature: designer dispatch names N files; recon-grep across the broader module template family finds N+M. For module-template audit-class fixes specifically (Logo / Page / Menu / Pictures / Teamcard / Posts / etc.), ALWAYS run the cross-file diagnostic `grep -rln '<pattern>' Modules/<Name>/resources/views/templates/*.blade.php` before shipping — bundle the extras into the same fix slice with a recon-multiplier note in the SHIP report. AI-809's recon found 2 extra files (images + navbar) beyond designer's 4-named (default + simple + small + skin-1); 33% of installs would have been left vulnerable post-ship without the recon delta. Same defect family as the AI-815 "audit-maturity-as-defense" insight — first-audit modules have HIGH recon multiplier; mature modules have x1.0.
- **Applies when:** Authoring ANY PHPUnit contract test that asserts the ABSENCE of a literal source token. Especially common in: audit-cleanup ships (the removed legacy pattern is referenced in "before/after" docblock prose); Stage-1 consumer-wiring tests (commented-out call site is the negative-assertion target); Stage-3 propagation-without-renderer-update tests ("what was removed" prose appears alongside the negative assertion); Stage-5 template-attribute-escape-leak fixes (rewritten file's docblock describes the corrupted attribute shape). **Skill-file promotion candidate** at 17+ recurrences (well past the 3+ promotion bar); designer explicitly flagged "definitely tier-1 codify when LESSONS next consolidates" — documented as the canonical sub-rule of the parser-meaningful-character family until explicit human direction to author `.claude/skills/selector-self-match-guard/SKILL.md`.

## 2026-05-17 — Parser-meaningful-character family promoted to 4-recurrence + unified meta-rule: any character/sequence with meaning to ANY upstream parser must be escaped or rephrased even inside an apparently-inert context

- **Pattern:** AI-806 (task-2026-05-17-aeb113, commit `9d2e083121`) — Page-template rewrite needed to document the removed legacy `<?php print $item['title'] ?>` pattern in a PHP `//` source comment, but a literal `?>` in a `//` comment terminates PHP code mode at the `?>` (PHP parser exits `<?php ... ?>` at the first `?>` regardless of comment context — the comment is parsed AFTER PHP-mode detection). Fix shape: rephrase the prose as `"the legacy unescaped php-print pattern. PHP exits code mode at ?>"` only when the comment is on its own line AND followed by a newline that re-enters PHP via `<?php`, OR (cleaner) drop the literal token entirely from the prose — `"the legacy unescaped php-print pattern"` carries the same meaning without the parser-meaningful sequence. Designer's Round 13.2 ACK formalised this as the **4th session-occurrence** of the parser-meaningful-character family. **Full family roster:**
  - **(1)** Alpine `x-data="..."` embedded `"` terminates the HTML attribute at the first `"` regardless of surrounding `/* */` or `//` comment context — AI-692 + AI-790 (Alpine x-data factory-extraction is the robust fix).
  - **(2)** PHP docblock prose containing literal `*/` terminates the docblock at the `*/` regardless of surrounding prose — AI-790 (rephrase as words: "slash-star-style block comment").
  - **(3)** Blade `@<directive>` tokens inside CSS docblock comments embedded in `<style>` blocks parse as Blade directives even inside `/* */` CSS comments — AI-796 + AI-803 (rephrase as "else-branch" / "if-statement" / "end-of-if").
  - **(4)** PHP `?>` literal inside a `//` line comment exits PHP code mode at the `?>` regardless of comment context — AI-806 (rephrase or drop the literal token; "the legacy unescaped php-print pattern" without the literal `?>` sequence).
  - **(Bonus, sister family)** VitePress `{{ expression }}` in markdown prose or inline backticks (outside fenced code blocks) is parsed by Vue at SSR — AI-326 docs hardening sweep (escape with `&#123;&#123;`).
- **Why it happens:** Each instance is the same mental-model bug — author assumes "this is inside a comment, the upstream parser will skip it." False at every layer. Comments are a LEXER-level concept; the lexer reaches the comment AFTER tokenisation. Parser-meaningful characters (`"`, `*/`, `@<directive>`, `?>`, `{{`) terminate or alter their enclosing structure at the LEXER stage, before the comment is recognised. The unifying mental model that prevents the bug: **comments are not safe containers for parser-meaningful tokens; they're inline text the parser sees in the same pass as the surrounding code.**
- **Prevention rule (unified meta-rule):** **Any character or sequence with meaning to ANY upstream parser MUST be escaped or rephrased even inside an apparently-inert context** — `//` line comments, `/* */` block comments, CSS comments inside `<style>`, prose inside `@php @endphp`, prose inside docblocks, JS template literals, HTML attribute values, markdown prose. The canonical fix shape is **rephrase to remove the literal token from prose**, NOT escape it. Examples: "slash-star-style block comment" not `*/`; "the else-branch" not `@else`; "the legacy php-print pattern" not `?>`; "the HTML-attribute quote terminator" not the bare `"`. Contract-test regression guard pattern: assert the affected source file does NOT contain the literal parser-meaningful token outside of its legitimate code-mode use. Same family lineage now spans 4 distinct token classes + 1 markdown sibling; codify the meta-rule when authoring ANY new comment / docblock / prose surface that references removed-code patterns.
- **Applies when:** Authoring or auditing any source file with embedded prose that references the SHAPE of removed/legacy code. ESPECIALLY common in Blade view rewrites + Filament resource refactors + Alpine factory extractions + PHP class deprecations — anywhere the docblock explains "what this used to be" using literal tokens from the prior shape. The recurrence rate is now 4 in one session; future contract tests should preemptively pin parser-meaningful-token absence in the rewritten source as a regression guard. Reference instances (chronological): AI-692 (HTML attribute `"`) → AI-790 (PHP docblock `*/` + Alpine x-data `//` line-comment `"`) → AI-796 + AI-803 (Blade `@<directive>` in CSS docblock) → AI-806 (PHP `//` line-comment `?>`).

## 2026-05-17 — Filament's `->hiddenLabel()` removes the label from the AT tree (WCAG 3.3.2 Level A failure) — use sr-only positioning instead

- **Pattern:** AI-817 (task-2026-05-17-04f015) — Create Post / Create Page / Create Product title input on the live-edit canvas was emitted via `TextInput::make('title')->hiddenLabel()->placeholder("What's the page title?")`. The visual hide was working as intended (placeholder-only affordance, compact wizard chrome) — but `->hiddenLabel()` renders the rendered DOM with NO `<label>` and NO `aria-label` on the input, so screen-reader users hear nothing when the input gets focus. WCAG 2.1 SC 3.3.2 Level A failure. Closely-related Stage-5 failure-family member because the visual fix (cosmetic) silently destroyed the AT contract (semantic). Same class as AI-804 (empty `alt=""` on logo).

## 2026-05-17 — Contract-test source slicing: never bound on `strpos($source, ';', ...)` when surrounding docblock prose may contain semicolons

## 2026-05-17 — Stage-6 JS-context-escape-leak: Blade `{{ }}` HTML-escapes but does NOT JS-escape

- **Pattern:** Designer's Round 14.2 audit (task-2026-05-17-4054e4 STATUS roll-up, dispatched after AI-814 ship) explicitly proposed codifying a **new Stage in the failure-family taxonomy**: "JS-context escape is its own Stage — Blade `{{ }}` doesn't help here." The AI-814 defect is the canonical instance: `description: "{{ $item['title'] }}"` interpolated inside a `<script>` block. Blade's `{{ }}` HTML-escapes (`<` → `&lt;`, `&` → `&amp;`, `"` → `&quot;`, etc.) but `<script>` content is NOT subject to HTML entity decoding by the browser. A title containing `</script><script>alert(1)</script>` would be HTML-escaped to `&lt;/script&gt;...` (literal text inside the JS string, safe in modern browsers) — BUT a title containing a literal `"` becomes `&quot;` which is rendered as 6 literal characters inside the JS string, not as `"`. The string still doesn't break out, BUT the rendered content is corrupted (display shows `John&quot;s` instead of `John"s`). More importantly, depending on browser + Content-Security-Policy + locale + Blade-render order, **defense-in-depth requires JS-context-aware escape**, NOT HTML-context. Confirmed surfaces: AI-814 (Pictures module gallery<rand> script block) — 6 templates. Sibling to Stage-5 template-attribute-escape-leak (AI-692/AI-790 — HTML attribute context); Stage-6 covers the `<script>` block JS-string-literal context.
- **Why it happened:** Blade `{{ }}` is the project's canonical "escape for safe output" idiom. Developers reasonably assume `{{ }}` is universally safe across HTML / attribute / script / style contexts. It isn't: each context has its own escape rules. `{{ }}` is wrong for JS-string-literal context (use `json_encode()` with JS-context flags), wrong for CSS-value context (use a sanitised allowlist), and risky for HTML-attribute context if the attribute body contains JS expressions (AI-692 Alpine x-data lineage). The unifying mental-model bug is "HTML escape = safe everywhere" — false. Designer crystallised the lesson: *"Blade `{{ }}` doesn't help here, you need `json_encode()` with `JSON_HEX_*` flags OR move the data to a `data-` attribute and read it via JS."*
- **Prevention rule:** Never interpolate user-controllable data directly inside a `<script>` block via Blade `{{ }}`. Two canonical safe patterns: **(A) `json_encode($data, JSON_HEX_QUOT | JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS)`** — escapes `"`, `<`, `>`, `&`, `'` as `\uXXXX` sequences inside the JSON output; ship as `<script>window.foo = @php echo json_encode(...); @endphp;</script>`. **(B) Move the data to a `data-*` attribute on a static DOM node** (where Blade `{{ }}` IS the correct escape because HTML attribute context decodes entities), then read in JS via `JSON.parse(el.dataset.foo)`. Pattern (A) is preferred for inline initialisation; pattern (B) is preferred for data that's already DOM-bound. Wrap any initialisation in an IIFE `(function () { ... })();` to avoid global scope pollution, AND use explicit `window.foo = ...` assignment if the global IS intentional so external readers find it by name. Reference: AI-814 / task-2026-05-17-8cf71e — 6 Pictures templates closed by this recipe.
- **Applies when:** Authoring any Blade template that emits a `<script>` block containing variables sourced from user-controllable data (`$item['title']`, `$post['description']`, `$user['name']`, `$content_id`, anything from the request, anything from the database). ESPECIALLY when initialising JS gallery / lightbox / modal / autocomplete data structures inside `<script>` blocks where multiple per-item values are interpolated. Family lineage: Stage-5 (HTML-attribute-escape-leak — AI-692/790) + Stage-6 (JS-context-escape-leak — AI-814, this entry).
- **Diagnostic-grep refinement (codified post-AI-814 from Round 14.2 STATUS roll-up false-positive audit):** the naive single-regex prong `grep -rE '<script>...\{\{[^}]+\}\}...</script>'` does NOT work reliably because Perl/PCRE regex engines do not respect `</script>` as a tag boundary — non-greedy `[\s\S]+?` happily spans multiple `<script>...</script>` blocks PLUS the intervening HTML, producing false matches like the AI-814 cycle's 9 false positives across 7 modules (Accordion / BeforeAfter / Captcha / Cart / CustomFields / HighlightCode / Menu / Pictures-slick). All 9 turned out to interpolate only TRUSTED data sources (`{{ $params['id'] }}`, `{{ asset() }}`, `{{ __() }}`, `{{ admin_url() }}`, `{{ get_option() }}`, `{{ app()->getLocale() }}`, `{{ $id }}`, `{{ $before }}`, `{{ $for_id }}`, `{{ $edit_field_key }}`). **Correct diagnostic methodology:** use a per-script-block scanner (Python / `awk` / `perl -0777` with explicit `(?:(?!</script>).)*?` non-crossing-tag pattern) — NOT a single-line `grep` regex. The scanner extracts each `<script>...</script>` block as a discrete unit, then asserts the script body contains a Blade interpolation of the shape `\{\{\s*\$(item|post|content|user|comment|record|product|category|page)\[` (user-data array-field access). Reference Python implementation lives in `/tmp/` for ad-hoc audit runs — `grep` alone is insufficient. **General lesson for all stage-family diagnostics:** (a) prefer per-construct scanners over single-line regexes when the construct boundary matters; (b) always exclude trusted-helper-output patterns from the prong; user-data array-field access is the canonical defect signature.

- **Pattern:** task-7326d6 AI-700 MainDrawer was a `<Teleport to="body">` Vue component that mounted at `document.body` root (outside the `.mw-live-edit-page` wrapper). ## 2026-05-16 — Vue `:class` + `class` split for state-class triads — never combine static + dynamic in one map

- **Pattern:** task-8b10a3 AI-699 SaveButton first draft used a single `:class="{ 'btn btn-dark live-edit-toolbar-buttons mw-save-button': true, 'mw-save-button--has-changes': _dirty, 'mw-save-button--idle': !_dirty }"` map — bundling the static legacy classes (`btn btn-dark live-edit-toolbar-buttons`) and the always-true new class (`mw-save-button`) into a single combined string. ## 2026-05-16 — `/* … */` block comments inside an HTML attribute value terminate the attribute at the first embedded `"`

- **Pattern:** task-968a71 first-attempt at the AI-692 two-group Add-Content modal embedded a block comment in the `x-data="..."` Alpine attribute that contained prose like `/* typing "page" hides the "On this page" group header */`. The HTML attribute parser doesn't know the `"` is inside a JS comment — it sees the first `"` and closes the attribute. Result: the entire x-data block was silently truncated, the page paint succeeded, and Alpine then threw a cascade of `q is not defined` / `hasVisibleCardsInGroup is not defined` / `resultAnnouncement is not defined` ReferenceErrors. The bug was invisible until DevTools console was opened.
- **Why it happened:** Block comments inside HTML attribute values look fine in editors with JS syntax highlighting because the editor treats the attribute body as JS — but the browser's HTML parser runs first and only knows about `"`. Any character with parser-level meaning (here `"`, but `</` is the same family) is unsafe in attribute prose, regardless of language wrapping.

Use `//` single-line comments only, and keep them quote-free. The same rule applies to embedded `</script>` strings — never reproduce a parser-meaningful sequence in prose inside that parser's scope. Reference: regression-guard test `comment_block_uses_single_line_comments_only_in_xdata` in `AddContent968a71AI692TwoGroupLayoutContractTest.php` asserts no `/*` appears inside `x-data="..."`.
- **Applies when:** Authoring any Alpine `x-data` / `x-init` / `x-on:*` block longer than ~5 lines, especially when the block contains JS comments describing the helper's behaviour. The PHP docblock variant: literal `*/` inside docblock prose closes the docblock — express as words ("slash-star ... star-slash") rather than characters.

## 2026-05-16 — Tailwind v4 uses native CSS `translate` property — independent of `transform`

- **Pattern:** task-02760c (Live Edit sidebar menu invisible after hamburger click) hit a silent regression where the project's `.fi-sidebar { transform: translateX(-100%) !important }` override appeared to do nothing. DevTools confirmed `transform: matrix(1, 0, 0, 1, 0, 0)` (identity!) but `getBoundingClientRect().x === -280`. Root cause: Tailwind v4 compiles utilities like `-translate-x-full` to the **native CSS `translate` property** (`translate: -100% !important`), NOT to `transform: translateX(...)`. CSS `translate` is its own property — independent of `transform` — and the Tailwind utility wins because the project override never touches it.
- **Why it happened:** The `transform: translateX(...)` mental model is the Tailwind v3 / pre-2022 CSS shape; Tailwind v4 adopted the newer CSS individual-transform properties. Project-side overrides written against v3 muscle memory silently miss the v4 generated CSS.
- **Prevention rule:** When defeating any Tailwind v4 translate/rotate/scale utility, reset BOTH the individual property AND the composite `transform`: `translate: none !important; transform: translateX(-100%) !important;` (also `rotate: none !important;` / `scale: none !important;` as applicable). Validate with `getComputedStyle(el).translate` not just `.transform`. Always reproduce at the failing viewport with Playwright + `evaluate(() => getBoundingClientRect())` before declaring the override correct.
- **Applies when:** Any project-side CSS attempting to override a Tailwind v4 utility that animates element position. Common spots: Filament sidebar/topbar visibility toggles, modal slide-in/out, drawer opens.

## 2026-05-14 — Contract-test regexes need non-greedy `.*?` for JS function bodies containing `)`

- **Pattern:** Wrote a contract test asserting an addEventListener call existed in JS source: `'/document\.addEventListener\(\s*\'click\',\s*function\(e\)\s*\{[^)]+\},\s*true\s*\)/s'`. The test failed even though the JS was present.
- **Why it happened:** `[^)]+` excludes any `)` character, but the function body legitimately contains parentheses (method calls like `e.target.closest('.fi-form')`). The character-class was the wrong tool.

## 2026-05-17 — Audit-maturity-as-defense: an audited surface stays audited; recon-multiplier inversely correlates with audit-cycle count

- **Pattern:** Designer's Round 14.3 STATUS (task-2026-05-17-fb0686, sent after AI-815 ship) explicitly flagged: *"Strong signal: an audited surface STAYS audited. Category has been touched 6+ times across prior cycles and is now defect-resistant."* This crystallises a meta-observation visible across the 2026-05-17 chrome arc: the recon-multiplier (designer-named-instances vs recon-found-instances) is **inversely correlated** with how many prior audit cycles the touched module has experienced. **Empirical evidence from this session** (per AI-815 SHIP report recon-history table): **Pictures (1-2 prior audit cycles)** → AI-812 ×34, AI-813 ×20, AI-814 ×6 / **Menu (recent audit)** → AI-809 ×1.5 / **Category (6+ prior cycles: TICKET-UU + TICKET-AT + TICKET-SS + TICKET-V + TICKET-CX + AI-82 + AI-815)** → AI-815 ×1.0 (all 4 templates designer-named matched recon exactly). Empirical confirmation post-AI-815: ran the 4-prong legacy-Blade audit class diagnostic + Stage-6 JS-context scanner across Category — **0 residual defects across all 4 prongs**. Category is the "reference template for what other modules should look like after the legacy-Blade umbrella ships" per designer's framing.
- **Why it happens:** Each audit cycle removes a class of defects from the touched surface AND raises the bar by documenting fix-patterns + adding contract tests + embedding task-id markers. Subsequent audits on the same surface find fewer defects because (a) the obvious ones are already fixed, (b) future contributors who copy-paste from the surface inherit the fixed shape, (c) the contract tests catch regressions early. Conversely, a module with no audit history accumulates defects silently — copy-paste from siblings, untouched legacy code, no contract test coverage — so the FIRST audit cycle has a massive multiplier (Pictures ×34 example) because all the defects surface at once. The audit-cycle history acts as a defect-resistance ratchet.
- **Prevention rule:** Use audit-cycle history as a **scoping signal** for dispatch sizing. Modules with no/few prior audit cycles → expect HIGH recon multiplier on first dispatch in a defect-class → plan for batch ship + Python-script automation + comprehensive contract test with DataProvider over the full file set. Modules with 6+ prior audit cycles → expect ×1.0 multiplier → designer-named scope is usually comprehensive; ship per-file Edit calls without batch-script overhead. Documented dispatch-scope estimation heuristic (cumulative from this session): (1) **Designer email framing matters** — "every X" / "all gallery images" / broad scope language → high multiplier likely; explicit "all 4 templates" enumeration → ×1.0 likely (per AI-815 vs AI-812 contrast). (2) **Module age matters** — pre-Filament templates (Logo / Page / Menu / Pictures / older Pictures skins) → higher multiplier likely; recently-refactored modules (Category, post-AI-82) → ×1.0 likely. (3) **Audit-cycle density matters** — count distinct `task-YYYY-MM-DD-XXXXXX` markers in source as a proxy for prior audit-cycle count; high marker density = mature surface. **Diagnostic verification step**: AFTER shipping a dispatch on a "mature" surface, run the 4-prong legacy-Blade diagnostic + Stage-6 Python scanner against the touched module to empirically confirm "0 residual defects" — if the count is nonzero, the maturity claim is wrong and a recon-delta surfaces (this verification ran post-AI-815, Category = 0 residual confirmed).
- **Applies when:** Estimating dispatch scope BEFORE running the per-file fix loop. The maturity signal helps decide between "single Edit call for the designer-named instance" vs "Python batch script + DataProvider contract test for the recon-delta full module sweep". Also applies to **target-state framing for future audits**: the legacy-Blade umbrella's success criterion can be measured as "all 5 audit-class modules (Logo / Page / Menu / Pictures / Category) reach Category-level maturity = ×1.0 multiplier on subsequent dispatches" — that's the codified definition of "umbrella ticket done."

## 2026-05-17 — Stage-6 JS-context-escape-leak: Blade `{{ }}` HTML-escapes but does NOT JS-escape

- **Pattern:** Designer's Round 14.2 audit (task-2026-05-17-4054e4 STATUS roll-up, dispatched after AI-814 ship) explicitly proposed codifying a **new Stage in the failure-family taxonomy**: "JS-context escape is its own Stage — Blade `{{ }}` doesn't help here." The AI-814 defect is the canonical instance: `description: "{{ $item['title'] }}"` interpolated inside a `<script>` block. Blade's `{{ }}` HTML-escapes (`<` → `&lt;`, `&` → `&amp;`, `"` → `&quot;`, etc.) but `<script>` content is NOT subject to HTML entity decoding by the browser. A title containing `</script><script>alert(1)</script>` would be HTML-escaped to `&lt;/script&gt;...` (literal text inside the JS string, safe in modern browsers) — BUT a title containing a literal `"` becomes `&quot;` which is rendered as 6 literal characters inside the JS string, not as `"`. The string still doesn't break out, BUT the rendered content is corrupted (display shows `John&quot;s` instead of `John"s`). More importantly, depending on browser + Content-Security-Policy + locale + Blade-render order, **defense-in-depth requires JS-context-aware escape**, NOT HTML-context. Confirmed surfaces: AI-814 (Pictures module gallery<rand> script block) — 6 templates. Sibling to Stage-5 template-attribute-escape-leak (AI-692/AI-790 — HTML attribute context); Stage-6 covers the `<script>` block JS-string-literal context.
- **Why it happened:** Blade `{{ }}` is the project's canonical "escape for safe output" idiom. Developers reasonably assume `{{ }}` is universally safe across HTML / attribute / script / style contexts. It isn't: each context has its own escape rules. `{{ }}` is wrong for JS-string-literal context (use `json_encode()` with JS-context flags), wrong for CSS-value context (use a sanitised allowlist), and risky for HTML-attribute context if the attribute body contains JS expressions (AI-692 Alpine x-data lineage). The unifying mental-model bug is "HTML escape = safe everywhere" — false. Designer crystallised the lesson: *"Blade `{{ }}` doesn't help here, you need `json_encode()` with `JSON_HEX_*` flags OR move the data to a `data-` attribute and read it via JS."*
- **Prevention rule:** Never interpolate user-controllable data directly inside a `<script>` block via Blade `{{ }}`. Two canonical safe patterns: **(A) `json_encode($data, JSON_HEX_QUOT | JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS)`** — escapes `"`, `<`, `>`, `&`, `'` as `\uXXXX` sequences inside the JSON output; ship as `<script>window.foo = @php echo json_encode(...); @endphp;</script>`. **(B) Move the data to a `data-*` attribute on a static DOM node** (where Blade `{{ }}` IS the correct escape because HTML attribute context decodes entities), then read in JS via `JSON.parse(el.dataset.foo)`. Pattern (A) is preferred for inline initialisation; pattern (B) is preferred for data that's already DOM-bound. Wrap any initialisation in an IIFE `(function () { ... })();` to avoid global scope pollution, AND use explicit `window.foo = ...` assignment if the global IS intentional so external readers find it by name. Reference: AI-814 / task-2026-05-17-8cf71e — 6 Pictures templates closed by this recipe.
- **Applies when:** Authoring any Blade template that emits a `<script>` block containing variables sourced from user-controllable data (`$item['title']`, `$post['description']`, `$user['name']`, `$content_id`, anything from the request, anything from the database). ESPECIALLY when initialising JS gallery / lightbox / modal / autocomplete data structures inside `<script>` blocks where multiple per-item values are interpolated. Family lineage: Stage-5 (HTML-attribute-escape-leak — AI-692/790) + Stage-6 (JS-context-escape-leak — AI-814, this entry).
- **Diagnostic-grep refinement (codified post-AI-814 from Round 14.2 STATUS roll-up false-positive audit):** the naive single-regex prong `grep -rE '<script>...\{\{[^}]+\}\}...</script>'` does NOT work reliably because Perl/PCRE regex engines do not respect `</script>` as a tag boundary — non-greedy `[\s\S]+?` happily spans multiple `<script>...</script>` blocks PLUS the intervening HTML, producing false matches like the AI-814 cycle's 9 false positives across 7 modules (Accordion / BeforeAfter / Captcha / Cart / CustomFields / HighlightCode / Menu / Pictures-slick). All 9 turned out to interpolate only TRUSTED data sources (`{{ $params['id'] }}`, `{{ asset() }}`, `{{ __() }}`, `{{ admin_url() }}`, `{{ get_option() }}`, `{{ app()->getLocale() }}`, `{{ $id }}`, `{{ $before }}`, `{{ $for_id }}`, `{{ $edit_field_key }}`). **Correct diagnostic methodology:** use a per-script-block scanner (Python / `awk` / `perl -0777` with explicit `(?:(?!</script>).)*?` non-crossing-tag pattern) — NOT a single-line `grep` regex. The scanner extracts each `<script>...</script>` block as a discrete unit, then asserts the script body contains a Blade interpolation of the shape `\{\{\s*\$(item|post|content|user|comment|record|product|category|page)\[` (user-data array-field access). Reference Python implementation lives in `/tmp/` for ad-hoc audit runs — `grep` alone is insufficient. **General lesson for all stage-family diagnostics:** (a) prefer per-construct scanners over single-line regexes when the construct boundary matters; (b) always exclude trusted-helper-output patterns from the prong; user-data array-field access is the canonical defect signature.

## 2026-05-17 — Stage-3 sub-case "viewport-scope leak": CSS rule meant for one viewport, declared at top-level, applies everywhere

- **Pattern:** task-2026-05-17-fa5dc3 (AI-803, P1 HIGHEST) — Logo invisible on every install. `Modules/Logo/resources/views/templates/default.blade.php` declared `.logo-module { min-width: 0; overflow: hidden }` UNCONDITIONALLY in its `<style>` block, despite a docblock immediately above explicitly stating the rule was meant for the narrow-viewport (≤390px hamburger-row) scenario. Effect: at every viewport (desktop included) the parent flex column collapsed to 0×0, so the SVG logo (300×82 natural) loaded but rendered invisible. Source-level contract tests would have passed (rule is present, syntactically valid); only a cross-viewport rendered-browser probe caught it. Designer description: "most expensive single-CSS-rule defect this session — silent, source-only-test-passes, only catches at rendered-browser eye."
- **Why it happened:** Same defect family as the existing Stage-3 "propagation-without-renderer-update" sub-case (route propagates correctly but generic renderer ignores the new branch). New sub-case: a rule is mounted at the WRONG SCOPE — written with one viewport in mind but declared at a scope that applies to all viewports. The author's mental model — "the docblock explains the intent, so the scope is implicit" — fails because CSS doesn't read docblocks. Compounded by the fact that the visible damage (logo invisible) is on the production-default path, but the originating reasoning (narrow-viewport hamburger ergonomics) is buried in a single template's comments — easy to inherit without re-checking the scope.
- **Prevention rule:** Whenever a CSS rule's docblock OR adjacent prose describes the rule as "for narrow viewports" / "for mobile" / "when the hamburger collides" / "at <Npx" — the rule MUST live inside a `@media` block that matches that scope, not at top-level. Audit checklist when touching any template `<style>` block: (1) read every docblock above each rule and confirm the rule's actual scope matches the docblock's stated scope; (2) gate viewport-specific rules inside `@media (max-width: Npx)` (Bootstrap 5 sm=575px / md=767px / lg=991px / xl=1199px); (3) cross-viewport-safe rules (responsive-image safety like `.logo-module img { max-width: 100%; height: auto }`) stay outside the media query — those genuinely apply at every viewport. Contract tests targeting top-level scope MUST slice the `@media (max-width: NNNpx) { ... }` block OUT (`preg_replace('~@media\s*\(max-width:\s*575px\)\s*\{(?:[^{}]*|\{[^{}]*\})*\}~s', '', $stripped)`) before asserting absence of narrow-viewport declarations at top-level scope — otherwise the test false-fails on the legitimate gated rule.
- **Applies when:** Touching any template `<style>` block (Logo, Slider, Hero, any module that ships its own inline CSS) where the styling has mobile-specific intent. ESPECIALLY when the rule sets `min-width: 0` / `overflow: hidden` / `position: fixed` / `display: none` / anything that aggressively constrains layout on a flex/grid parent — those rules need viewport scope discipline because their cross-viewport behaviour is destructive.

## 2026-05-17 — Blade `@<directive>` tokens inside CSS docblock comments crash the Blade compiler (2-recurrence promotion)

- **Pattern:** Now 2 session-recurrences. (1) task-2026-05-17-0e6cfa (AI-796 cart empty-state) — wrote `/* Livewire CartItems @else branch renders ... */` inside a CSS docblock in `<style>` block; Blade crashed live page with "syntax error, unexpected end of file, expecting elseif/else/endif". (2) task-2026-05-17-fa5dc3 (AI-803 Logo SCSS) — wrote prose describing the AI-805 dead-conditional block including the literal `@if(is_live_edit())` token in a CSS docblock; same crash. Both bugs invisible to source-level contract tests (compile-stage failure happens before any test fixture loads); both invisible to `php -l` (syntactically valid PHP because Blade compilation is a separate pass).
- **Why it happened:** The Blade compiler (`Illuminate\View\Compilers\BladeCompiler`) parses `@<directive>` tokens with regex passes BEFORE CSS comments are recognised as comments — CSS `/* ... */` is plain text to Blade. The Blade `@if` / `@else` / `@elseif` / `@endif` directives need balanced opening/closing pairs; when a `@if(` appears in prose without a matching `@endif`, Blade walks to EOF looking for one and fails with the line-anchored compile error. Symmetric: `@else` / `@endif` appearing without a preceding `@if` opener also confuse the matcher. The author's mental model — "this is inside a CSS comment, the compiler will skip it" — is wrong because Blade doesn't know CSS.
- **Prevention rule:** Never write literal `@if(` / `@else` / `@elseif` / `@endif` / `@switch(` / `@case(` / `@foreach(` / `@for(` / `@while(` tokens inside ANY content embedded in a Blade view — including CSS comments inside `<style>`, HTML comments, JS template literals inside `<script>`, prose inside `@php ... @endphp` blocks. Rephrase: "the if-statement at line N" / "the else-branch" / "the end of the if-block" / "the at-if-paren-X-paren conditional"; or break the token sequence with prose-only words ("the directive that opens with at-if"). The rule applies to ANY content the Blade compiler sees — Blade reads the whole file before deciding what's a directive. Contract-test regression guard: assert the affected `<style>` block does NOT contain `/@(if|else|elseif|endif|switch|case|foreach|for|while)\b/` tokens. Same parser-meaningful-character family as: Alpine `x-data` corruption on embedded `"` (AI-692/790), PHP docblock termination on literal `*/` (AI-790), VitePress markdown `{{ … }}` SSR collision (AI-326).
- **Applies when:** Authoring any Blade view that contains `<style>` / `<script>` blocks with explanatory docblocks that reference Blade directives or describe Blade-templated behaviour. Especially common in module template `default.blade.php` files (Logo, Slider, Hero, Newsletter) where a single template carries DOM + CSS + Blade conditionals in one source.

## 2026-05-17 — Microweber `_e($str, true)` for translatable strings ending in `.` — Laravel `__()` returns empty

- **Pattern:** task-2026-05-17-0e6cfa (AI-796 cart empty-state) wrote `{{ __('Browse our products and add items.') }}` for the cart-empty body copy. The string rendered as `""` (empty) in the live page. Removing the trailing `.` from the string ("...and add items") made the string render correctly, confirming Laravel's translation key parser was treating the `.` as a namespace separator.
- **Why it happened:** Laravel's `__()` helper uses `.` as a translation-namespace separator (`__('messages.greeting')` looks up `greeting` inside the `messages` namespace). When the key is a literal English sentence ending in `.`, Laravel parses it as `'Browse our products and add items'` namespace + `''` empty key, returns empty, and the template renders the empty string. The Laravel docs document this but the silent-empty failure mode is easy to miss in code review.
- **Prevention rule:** For user-visible translatable strings (especially full sentences that naturally end in `.`) in Microweber Blade views, use the Microweber helper `_e('...', true)` instead of Laravel `__()`. The `_e()` second argument set to `true` enables translation while the helper handles the trailing-period case correctly. Confirm by greping existing patterns: `grep -rn "_e(.*true" Modules/ src/ Templates/` shows the canonical usage shape. Avoid `__()` for full English sentences in Microweber surfaces; reserve `__()` for dotted-namespace translation keys (`__('auth.failed')`).
- **Applies when:** Any user-visible Blade view, module template, or Livewire component that ships translatable English-prose copy. ESPECIALLY empty-state copy, button labels with trailing punctuation, alert messages, helper text — anywhere the copy naturally ends in `.` / `!` / `?`.

## 2026-05-17 — PHPUnit `#[DataProvider]` methods run pre-Laravel-boot — no `base_path()` / Laravel helpers

- **Pattern:** task-2026-05-17-918e58 (AI-799 MainDrawer users-href contract test) and task-2026-05-17-fe8f9e (AI-801 content-type fallback inference contract test) both shipped DataProvider methods that called `base_path()` to build absolute paths to source files. Both crashed with "Call to undefined method Illuminate\\Container\\Container::basePath()" before any test method executed. PHPUnit's `#[DataProvider]` attribute resolves DataProviders during test discovery / before each test method invocation — Laravel's application container has not booted at that point.
- **Why it happened:** PHPUnit DataProviders run in the test runner's pre-boot lifecycle; the Laravel application instance isn't bound to the container, so any Laravel helper that resolves through `app()` or `Application::class` throws. The mental model — "the test runner has access to the whole Laravel app" — is wrong for the DataProvider phase specifically. Test methods themselves DO have access (they run after Laravel bootstraps via TestCase setUp), but DataProviders don't.
- **Prevention rule:** Never call `base_path()`, `app()`, `config()`, `route()`, `Storage::`, `DB::`, `Cache::`, or any Laravel helper inside a `#[DataProvider]` method. Return relative paths (or other Laravel-helper-free data) from the DataProvider, then resolve per-test inside the test method via a helper: `protected function templateContents(string $relativePath): string { return (string) file_get_contents(base_path($relativePath)); }`. The DataProvider returns `['Modules/Content/resources/views/templates/default.blade.php', 'post']`; the test method receives those and calls `$this->templateContents($relativePath)` to read the file. References: `LiveEdit918e58AI799MainDrawerUsersHrefContractTest`, `CanvasFe8f9eAI801ContentTypeInferenceContractTest`.
- **Applies when:** Authoring any PHPUnit contract test that uses `#[DataProvider]` to parameterise over file paths, config values, or any Laravel-resolved data. Common with template-iteration tests (multiple Blade files), resource-list tests (multiple Filament resources), and route-introspection tests.

## 2026-05-17 — Pin the SHAPE, not the keyword — contract-test absence-asserts need the dead-pattern signature

- **Pattern:** task-2026-05-17-e2e29a (AI-805 dead-conditional Logo cleanup) initially asserted that the Logo template did NOT contain the bare `@else` token. False-failed because the template legitimately contains another `@else` in the image/text fallback chain (`@if(isset($logoimage)...) ... @elseif(...) ... @else <span>Click to add logo</span> @endif`). The bare-keyword absence assertion couldn't distinguish "the dead conditional with both arms returning `site_url()`" from "the legitimate fallback chain". Fix: anchor on the SPECIFIC dead-pattern signature `/@if\([^)]*\)[\s\S]*?site_url\(\)[\s\S]*?@else[\s\S]*?site_url\(\)[\s\S]*?@endif/` (both arms return `site_url()` — the dead-branch signature).
- **Why it happened:** Contract tests that grep for "this should be gone" assertions tend to use the simplest matcher (`assertStringNotContainsString('@else', $template)`). When the keyword has multiple legitimate uses in the same file, the absence assertion is too coarse — it false-fires on every legitimate occurrence and false-passes on dead occurrences that the keyword alone doesn't identify. The pattern is a cousin of the selector-self-match guard family (13+ session-recurrences): both fail when the assertion's specificity is wrong relative to what makes the defect specific.
- **Prevention rule:** When asserting absence of a code pattern, anchor on the SHAPE that makes the pattern DEAD rather than on a keyword that has other legitimate uses. Examples: (a) dead conditional both arms return same value → assert `/@if(...)X@else X@endif/` not bare `@else`; (b) commented-out call → assert `/^[\t ]*\/\/[\t ]*->descriptions\(/m` not bare `->descriptions(`; (c) legacy class name → assert `/class="[^"]*\bold-class\b/` not bare `old-class`; (d) removed import → assert `/^use [^;]*Old\\Namespace/m` not bare `Old\Namespace`. The general rule: identify what makes the defect specific (the relationship, the position, the context), and pin that — not the token in isolation.
- **Applies when:** Authoring any `assertStringNotContainsString` / `assertDoesNotMatchRegularExpression` against a file that may contain LEGITIMATE uses of the same keyword/token in unrelated positions. ESPECIALLY when refactoring removes a specific instance of a directive while leaving other instances intact (dead conditional collapse, partial-deprecation, scope reduction).

## 2026-05-17 — `mw()->ui->brand_name()` is the canonical helper — bare `brand_name()` does not exist

- **Pattern:** task-2026-05-17-f141ff (AI-794 auth chrome) first draft of `src/MicroweberPackages/User/resources/views/layout.blade.php` used `{{ brand_name() }}` for the site name. Laravel threw `Error: Call to undefined function brand_name()` at render time — there is no global `brand_name()` function in the project. The canonical helper is `mw()->ui->brand_name()` (via the `UiBuilder` service resolved off the Microweber app facade). Same shape for the brand logo: `mw()->ui->admin_logo()` / `mw()->ui->admin_logo_login()` — never bare `admin_logo()`.
- **Why it happened:** Microweber's `mw()->ui->` pattern is the canonical access path for chrome helpers (brand name, logo URLs, theme settings). Some agents (and historical code) have used bare global function names that look like Laravel helpers but were never registered as globals in this project. ## 2026-05-16 — `/* … */` block comments inside an HTML attribute value terminate the attribute at the first embedded `"`

## 2026-05-16 — Tailwind v4 uses native CSS `translate` property — independent of `transform`

- **Pattern:** task-02760c (Live Edit sidebar menu invisible after hamburger click) hit a silent regression where the project's `.fi-sidebar { transform: translateX(-100%) !important }` override appeared to do nothing. Always reproduce at the failing viewport with Playwright + `evaluate(() => getBoundingClientRect())` before declaring the override correct.
- **Applies when:** Any project-side CSS attempting to override a Tailwind v4 utility that animates element position. Common spots: Filament sidebar/topbar visibility toggles, modal slide-in/out, drawer opens.

## 2026-05-13 — Do not rely on a global `[x-cloak] { display: none }` rule

- **Pattern:** Added `x-cloak` to an Alpine-controlled empty-state element expecting the standard "hide until Alpine boots" behaviour. The element still flashed its `x-text` literal (`""`) on first paint.
- **Why it happened:** The project does not ship a global `[x-cloak] { display: none }` rule. `x-cloak` is a CSS-driven feature; without the rule, the attribute is inert.
- **Prevention rule:** For elements that must be hidden until Alpine has bound their state, use inline `style="display: none;"` as the default and let Alpine `x-show` toggle them. Belt-and-braces — works whether or not `[x-cloak]` is defined.
- **Applies when:** Any Blade view using Alpine `x-data` / `x-show` / `x-text` that has a visibly-different "uninitialized" state.

## 2026-05-13 — Empty-state copy must be static, not echo the user's query

- **Pattern:** Wrote `"No results for "<query>""` in an Alpine-bound empty state. Pre-Alpine paint rendered the literal `""` and looked broken.
- **Why it happened:** Alpine renders once before binding; user-typed values are unavailable on first paint. Combined with the missing `x-cloak` global rule, the unbound expression briefly leaks.
- **Prevention rule:** Keep empty-state strings static (e.g. "No content types found."). If the query value is genuinely needed, gate the entire empty-state block behind `x-show="..."` and inline-hide the wrapper.
- **Applies when:** Authoring Alpine-driven empty states for search/filter UIs (pickers, list filters, dropdown selectors).

## 2026-05-13 — Refactors without test content stay deferred

- **Pattern:** Considered sweeping 38 `text-align: left/right` and 21 `margin-left/right` rules to logical-property equivalents (`start`/`end` / `margin-inline-*`) as part of AI-293 RTL work. Did not ship.
- **Why it happened:** No RTL test content exists in the repo. Without a way to verify visually, the sweep risks LTR regressions on intentional left-aligned elements (data columns, label rows, mixed-mode contexts).
- **Prevention rule:** Bounded slice + contract test is the dominant winning pattern. Large mechanical refactors require either fixture data to verify against or an explicit dispatch from the PM. Flag the concern in the ship report and stop.
- **Applies when:** Any "rename across N files", "swap property across M rules", or other mechanical refactor where the only verification is "tests still pass" (which proves nothing about intent-bearing values).

## 2026-05-13 — Filament modal cancel API is `modalCancelActionLabel`, not `modalCancelAction(false)`

- **Pattern:** Wrote `->modalCancelAction(false)` intending to relabel the cancel button. Filament v5 rejected the call.
- **Why it happened:** Misremembered the API. `modalCancelAction(false)` *hides* the cancel button entirely (and may not be the v5 spelling).
- **Prevention rule:** To customize the label use `->modalCancelActionLabel('Cancel')`. To suppress the button use `->modalCancelAction(false)` only if v5 actually supports that signature on the action type — verify in `vendor/filament/` first.
- **Applies when:** Configuring Filament `Action` modals in any admin or checkout panel.

## 2026-05-13 — Window-event bridge handler names must match on both Live Edit surfaces

- **Pattern:** Added `liveEditInsertLayoutRequest` dispatch in `AdminLiveEditPage.php` without registering a matching listener in `iframe-page.blade.php`. The event fired and went nowhere.
- **Why it happened:** The two-surface architecture means each verb requires one dispatcher + one listener. Easy to add only the half that the current edit touches.
- **Prevention rule:** When adding a new admin↔iframe verb, edit BOTH `src/MicroweberPackages/LiveEdit/Filament/Admin/Pages/AdminLiveEditPage.php` and `src/MicroweberPackages/LiveEdit/resources/views/iframe-page.blade.php` in the same change. Grep for the verb name in both files to confirm both sides exist.
- **Applies when:** Any change that adds, renames, or removes a `CustomEvent` verb in the Live Edit communication bridge.

## 2026-05-13 — Built bundles win — always rebuild after touching `packages/<pkg>/resources/`

- **Pattern:** Edited a Vue SFC in `packages/frontend-assets/resources/assets/ui/components/Toolbar/` and verified visually before running the build. The dev server kept serving the prior bundle and the "fix" wasn't actually applied during the verification round.
- **Why it happened:** The Microweber runtime loads built JS/CSS bundles, not raw source. Source edits are invisible until rebuilt.
- **Prevention rule:** After any edit under `packages/<pkg>/resources/**`, run that package's build (`cd packages/<pkg> && npm run build`) BEFORE verifying or reporting. Pin a Memory rule: `feedback_always_build`.
- **Applies when:** Touching any `.vue`, `.scss`, `.css`, `.js`, or `.ts` file inside any subdirectory of `packages/`.
